# Java 源码解析：记忆、会话与输入历史

这份文档只按当前 TUI 实际执行的代码说明。主入口是 `MewCodeModel`，它把记忆能力接到聊天界面。

相关链路有四条：启动时加载规则和已有记忆；用户发消息时召回相关记忆；一轮结束后提取新记忆；会话和输入历史持续落盘。

先看整体调用关系。下面的顺序就是一次正常使用中各部分进入模型上下文或写回磁盘的顺序：

```text
TUI 初始化
  MewCodeModel.initializeAgent(...)
    -> new MemoryManager(workDir)
    -> MemoryManager.loadInstructions(workDir)
    -> buildMemorySection()
    -> Agent.setInstructions(...) / setMemoryContent(...)

用户发送消息
  MewCodeModel.sendUserMessage()
    -> 首次对话时 MemoryManager.injectMemories(...)
    -> SessionManager.saveMessage(...)
    -> HistoryStore.append(...)
    -> prefetchRelevantMemories(userText)
    -> Agent.setMemoryRecallFuture(...)

Agent 运行
  Agent.agentLoop(...)
    -> ConversationManager.injectLongTermMemory(...)
    -> 模型 / 工具循环
    -> 工具完成后，若召回已完成：addSystemReminder(recall)

本轮结束
  MewCodeModel.triggerMemoryExtraction()
    -> MemoryManager.extract(...)
  MewCodeModel.triggerMemoryConsolidation()
    -> MemoryConsolidator.maybeRun(...)
```

这四条链路用的都是同一个工作目录，但目的不同：指令是固定规则；自动记忆是跨会话保存的事实；会话是当前对话的完整记录；输入历史只服务于 TUI 的上下键。

## 1. TUI 初始化：先准备“固定上下文”

`MewCodeModel.initializeAgent(...)` 在 TUI 准备聊天时创建运行环境。

`MemoryManager` 读取规则和已有记忆，之后也负责提取新记忆。`MemoryConsolidator` 只负责以后整理重复或过时的记忆，此时不会运行。

`MemoryManager.loadInstructions(workDir)` 把 `MEWCODE.md`、`AGENTS.md` 等规则文件读成文本。它告诉模型“做事必须遵守什么规则”。

`buildMemorySection()` 把已有记忆变成类型、名称和描述组成的简介。它告诉模型“用户和项目以前有哪些长期事实”。

这两份文本先存入 `Agent` 字段，还没有发给模型。

用户提交消息、`Agent.run(...)` 启动后，`Agent` 才将它们插入 `ConversationManager`，随第一次请求发送。

```java
memoryManager = new MemoryManager(workDir);
instructionsContent = MemoryManager.loadInstructions(workDir);
memoryContentField = buildMemorySection();
agent.setInstructions(instructionsContent);
agent.setMemoryContent(memoryContentField);
```

`Agent.agentLoop(...)` 启动后，才调用 `ConversationManager.injectLongTermMemory(instructions, memoryContent)`。这一步把规则和记忆简介放到会话开头，因此第一次模型请求能看到它们。

`ltmInjected` 防止同一个会话反复插入。压缩后会重置这个标记，再次加入规则和简介。

### 指令从哪里来

`MemoryManager.loadInstructions(...)` 只负责委托。实际找文件和展开内容的是 `InstructionLoader.loadInstructions(...)`。

它会按低到高的顺序拼接以下来源，后出现的内容更靠近模型上下文末尾：

1. `~/.mewcode/MEWCODE.md`、`~/.mewcode/AGENTS.md`；
2. 从 Git 根目录到当前 `workDir` 每层目录中的 `MEWCODE.md`、`AGENTS.md`；
3. `workDir/.mewcode/INSTRUCTIONS.md`，作为旧格式兼容；
4. `workDir/MEWCODE.local.md`，作为本机私有覆盖。

每个文件会带来源标签后再拼接。

`InstructionLoader.expandIncludes(...)` 会展开 `@./...`、`@../...`、`@~/...` 和绝对路径。最大递归深度是 5；代码块里的 `@...` 不处理，也不会重复读取同一个文件。

## 2. 自动记忆存在哪里：Markdown 是唯一数据源

`MemoryManager` 只保留用户级记忆，目录是 `~/.mewcode/memory/`。

只有两个类别文件：`user.md` 保存用户偏好和长期习惯；`feedback.md` 保存用户纠正和验证过的协作规则。

写入主链是 `MemoryManager.extract(...) -> writeMemoryFile(...)`。它按 type 找到 `user.md` 或 `feedback.md`，再追加或覆盖其中的同名 `## 记忆名` 小节。

```text
MemoryManager.writeMemoryFile(...)
  -> ~/.mewcode/memory/user.md
  或 ~/.mewcode/memory/feedback.md
```

同名记忆再次提取时，`writeMemoryFile(...)` 替换对应 `##` 小节；没有该小节才追加。文件数量固定为两份，不会随记忆条目增加。

`MemoryManager.getMemories()` 读取两个类别文件的 `##` 标题和 Description，生成 `[type] name — description` 简介。

`MemoryManager.buildSystemReminder()` 用于首次对话。它只列出 `user.md` 和 `feedback.md` 的路径。

## 3. 用户发送消息：保存当前输入，并异步找相关记忆

普通输入进入 `MewCodeModel.sendUserMessage()` 后，先判断会话是否为空。

新会话的第一条消息会调用 `memoryManager.injectMemories(conversation)`。它加入两个类别文件的路径和一条确认消息；非空会话不会重复加入。

随后它把用户消息加入内存会话，并调用 `SessionManager.saveMessage(...)` 写入会话 JSONL。

它还调用 `historyStore.append(...)` 保存输入历史，然后启动 `prefetchRelevantMemories(userText)`。召回不等待结果，所以不会卡住 TUI。

```java
var prefetchFuture = prefetchRelevantMemories(userText);
agent.setMemoryRecallFuture(prefetchFuture);
Thread.startVirtualThread(() -> agent.run(conversation));
```

`prefetchRelevantMemories(...)` 使用独立的 `LlmClient`。它不会共享主对话的 system prompt。

它把用户问题、文件名和 description 交给 `MemoryRecall.findRelevantMemories(...)`。选择模型只能返回候选列表中真实存在的文件名。

得到文件名后，`MemoryRecall.renderReminder(...)` 才读取完整 Markdown 内容。

Future 最多运行 8 秒，但界面不等待。第一轮工具结束后，`Agent` 发现它已经完成才调用 `conv.addSystemReminder(recall)`；第二轮模型请求才能看到相关记忆。

此外，工具注册表还注册了 `MemorySearchTool`。它不走自动召回链，而是搜索 `user.md` 和 `feedback.md` 的正文，按关键词命中次数排序，最多返回 8 条结果。

## 4. 一轮对话结束：从近期对话提取新记忆

TUI 收到 `AgentEvent.LoopComplete` 后，调用 `triggerMemoryExtraction()`。

它先检查 `shouldExtract()`，再在虚拟线程执行 `MemoryManager.extract(...)`，因此不会挡住本轮聊天结束。

当前 `EXTRACTION_INTERVAL` 是 `1`，即每个完成的 Agent 回合都会尝试一次，而不是每 5 轮。不过 `extract(...)` 会在消息少于 4 条时立即返回，避免刚开始的短对话触发模型调用。

`MemoryManager.extract(...)` 只序列化最近 40 条消息。工具结果也会加入，每条最多 1,000 个字符。

因此测试、构建和 lint 输出可以成为记忆证据。`scanExistingMemories()` 还会提供已有记忆清单，提示模型更新同主题文件而不是重复创建。

提取模型必须输出 `MEMORY_NAME`、`MEMORY_TYPE`、`MEMORY_DESC`、ACE 三字段和 `MEMORY_BODY`。每条记忆用 `---` 分隔。

`extract(...)` 从流式 `TextDelta` 收集文本，遇到 `StreamEnd` 或 `Error` 停止。线程被中断时会恢复中断标记。

`AceBullet` 是一条记忆的证据链。Evidence 写实际观察到的内容；Inference 写模型据此得出的结论；Verification 写测试或检查结果。

`AceBullet.render(...)` 将这三段和 `MEMORY_BODY` 写进同一个 Markdown 文件。提取 prompt 要求模型不能把未验证推断写成事实，也不能编造验证结果。

解析时，没有名称或正文的块忽略。不是 `user` 或 `feedback` 的类型直接忽略；有效条目最后进入 `writeMemoryFile(...)`。

`MemoryManager.parseTypedSections(...)` 仍留在类中，能解析旧的 `### type` 格式，但当前 `extract(...)` 不调用它。它属于兼容/遗留辅助方法，不是现在的主提取链。

## 5. 后台整理：不是每轮都重写记忆

同一个 `LoopComplete` 还会调用 `triggerMemoryConsolidation()`，再进入 `MemoryConsolidator.maybeRun(...)`。

它只在四个条件都满足时启动：记忆目录存在、距上次至少 24 小时、期间至少有 5 个会话、距上次扫描超过 10 分钟。

通过门槛后，它用 `.mewcode/memory/.consolidate-lock` 加锁，再启动一个最小化的后台 Agent。

该 Agent 读取会话、`user.md` 和 `feedback.md`，用 `WriteFile`、`EditFile` 合并重复小节。

它能根据新的验证修正 ACE 的 Inference，但不能把未验证推断升级为事实。这就是当前的“知识演绎”：整理 Agent 基于已有证据修正 Markdown，而不是独立知识图谱。

## 6. 会话持久化：保存当前会话，不等于自动记忆

自动记忆用于未来会话。`SessionManager` 用于恢复当前聊天。

`sendUserMessage()` 和接收 assistant 完整回复的位置都会调用 `SessionManager.saveMessage(...)`。

记录写入 `.mewcode/sessions/<sessionId>.jsonl`。普通消息包含 `role`、`content`、`ts`。

现在的 `SessionManager.SessionMessage` 不再只是三个字段，而是：

```java
record SessionMessage(String role, String type,
                      String content, long timestamp, String toolUseId)
```

`type` 可标识 `compact_boundary`。`toolUseId` 用于工具调用链恢复。

新会话 ID 格式是 `yyyyMMdd-HHmmss-xxxx`。末尾随机四位十六进制避免同一秒冲突。

恢复时，TUI 先调用 `SessionManager.loadSession(...)`，再调用 `SessionManager.rebuildConversation(...)`。

没有压缩边界时，所有普通消息按 role 重放。有 `compact_boundary` 时，只重建“旧消息摘要 + 恢复块 + 最近消息 + 边界后的新消息”。

压缩前的旧记录仍留在 JSONL 供审计，但不会再次传给模型。

`listSessions(...)` 会逐个读取 JSONL，取得首条用户消息和消息数，再按修改时间倒序排列。

它还会读取当前 Git 分支名。因此会话很多且文件很长时，打开恢复列表仍有全量读取成本。

## 7. 输入历史：只服务 TUI 编辑框

`HistoryStore` 与 `SessionManager` 无关。它保存 `~/.mewcode/prompt_history.jsonl`，供用户用上下键找回输入。

`SessionManager` 保存模型对话，用于恢复会话。每次用户输入，`sendUserMessage()` 都调用 `historyStore.append(userText)`。

`HistoryStore.append(...)` 只去除连续重复输入，最多保留 200 条。超过上限会删最早内容，再全量重写 JSONL。

重写时所有保留条目使用这次刷盘的时间。因此这里的 `ts` 不是每条输入最初输入的精确时间。

## 8. 读代码时应区分的三件事

1. `SessionManager` 记录“这次对话说过什么”，恢复同一个会话使用；它不是跨会话知识库。
2. `MemoryManager` 把模型提炼出的长期事实写进 `user.md` 或 `feedback.md`；首次对话会注入文件路径，Agent 启动时会注入记忆摘要。
3. `MemoryRecall` 针对当前问题挑选少量 Markdown 记忆，在第一轮工具后异步塞给下一轮模型；`MemorySearchTool` 则是模型主动扫描 Markdown 的另一条检索入口。

把这三者分开看，就能顺着当前代码找到每一份信息何时写入、何时传入模型，以及它会影响当前会话还是未来会话。
