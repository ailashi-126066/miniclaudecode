# 14　计划：先让我看修法，再允许改 parser.py

上一章的记忆让模型知道用户偏好先看例子，却不能代表用户已经同意这次修法。面对“修复 parser.py，并跑测试”，用户可能希望先确认修改范围。Plan 解决的是这个具体问题：先写一份方案，用户看过后再开始项目修改。

```text
用户输入 /plan 修复 parser.py，并跑测试
→ 读取代码，只写当前方案Markdown → 请求审阅
→ 用户反馈“补空输入测试” → 修改方案，再次审阅
→ 批准review或auto → 按当前这份内容执行
→ 运行结束或重启 → 旧批准不再给下一轮放行
```

Plan 不执行方案里的自然语言，也不是另一个模型循环。模型仍通过普通文件和命令工具工作，只是在每次操作前多一层“现在是否允许这样做”的检查。

## 第一步：先留出一份方案文件，项目代码暂时只读

TUI 把 `/plan` 交给 `AgentSession.enter_plan`。服务先确认没有另一轮任务或审批等待，再由 `PlanService.enter` 从当前会话身份生成方案 ID和固定路径。带着任务正文调用时，之后才启动普通模型运行；不带正文时只保存进入规划这件事，不能虚构模型已经读完项目。

规划期模型可以读 parser.py、找测试位置，也可以用普通 `write_file` 或 `edit_file` 把思路写到当前 `/plans/ID.md`。为什么写方案不算突破只读？因为 `PlanToolGate` 只给这个精确路径一个例外。模型试图直接改 parser.py 或运行外部命令仍会被拒绝；批准不是写在提示词里的一句劝告。

文件后端还有第二道限制。`PlanBackend` 只认当前方案文件，搜索前也把扫描范围缩到这个文件，而不是扫完整个内部计划目录再隐藏结果。因此方案工具能给用户展示完整 Markdown，又不会顺便暴露或修改别的会话方案。保存 `plan_state` 时先写日志，再更新内存和活动文件名，后面每一层才有一致依据。

## 第二步：把用户实际看到的正文固定下来，再等回答

模型写好方案后调用 `ExitPlanMode`。这是普通工具入口，`execute` 把当前运行信息交给 `PlanService.review`；它不会自己再建一个 Agent。服务读取真实 Markdown，将正文、路径、当前分支和内容的 SHA-256 摘要保存成 `plan_review`。这个摘要用来判断后来文件是否还是同一份，并不是用来替代用户阅读正文。

随后 `InterruptPlanPrompt.ask` 调用原生 LangGraph task，task 内的 `interrupt(payload)` 把问题交给界面并暂停当前图。用户可以反馈、批准后逐项审阅，或批准普通读写命令自动执行。反馈会保存为用户消息，让模型继续修同一份方案，例如补上空输入测试，然后再次请求审阅；它不会顺手获得项目写入权限。

用户最终选择批准时，框架恢复到等待处，服务先核答案对应的方案和操作，再重读 Markdown。只有内容与审阅时完全一致，才保存 `approved_hash` 与当前 `run_id`。如果审批期间有人从编辑器改了方案，就要求重新看过新内容。界面发送的答案不能直接替换服务里的批准状态。

## 第三步：批准以后，每次工具还要问“是不是刚才那份方案”

模型现在准备修改 parser.py。工具到达 `PlanToolGate` 时，`PlanService.guard` 检查批准是否属于当前运行，并核对方案文件是否仍与已批内容一致。批准后方案本身变成只读；若换了运行或正文改变，就退回规划，不能一边改授权内容一边按旧授权执行。

用户选 `review` 时，这层检查通过只表示方案仍有效，普通动作仍交原来的权限检查逐次询问。选 `auto` 时，Plan 门可直接放行普通 read、write、command，跳过它的普通父级审批；危险 Bash 命令的拒绝规则仍先处理。这里需要明确“自动”免掉的是哪一层，不能笼统说所有原审批仍被调用，也不能说全部工具获准。

团队合并和子助手命令还有更外面的强制检查。`TeamToolGate` 会为具体合并另做源代码与目标提交的预览并询问用户；`WorkerBoundaryGate` 固定子工作区和命令限制。它们不会因为普通 Plan 门提前返回而消失。下一章把测试分给子助手时，还会再次遇到这两道检查。

## 第四步：执行结束，或者明天重开，批准为什么都不续期

本轮修复和测试结束后，会话调用 `PlanService.finish`。只有批准记录里的运行 ID 与这轮相同，才把方案标为完成，并清除批准所绑定的运行。尚在规划中的方案不会被一次无关任务错误标成“已经做完”；自然语言里的勾选项也不能替代这次状态检查。

明天重新打开会话，`initialize` 从当前分支的日志重建方案，并检查磁盘路径确实属于这个会话。原来的 auto/review 会回到 planning，旧批准不跨进程续期。历史仍然能告诉用户昨天批准了什么，但新的任务必须建立自己的执行依据。切换分支时重新初始化，也是为了同一原因。

模型上下文中的方案提醒也要同步撤下。`PlanProjection` 只从日志生成路径和状态提示，总先清除自己上次留下的计划键，再按当前状态补入；完成后不会因旧压缩快照留下“还在执行计划”的提醒。它不读写 Markdown，也不授予权限。读完这里，就可以带着已确认的任务范围去看团队怎样分工。

## 框架在刚才的故事里做了什么

Plan 服务没有继承 `AgentMiddleware`。框架负责的第一件事是文件工具：`FilesystemMiddleware` 使用组合后端，`/plans/` 路由指向 `PlanBackend`，后者组合实际文件后端并限制精确文件。模型仍调用熟悉的读写工具，只是这个路由的真实文件范围更窄。

第二件事是等待用户：`InterruptPlanPrompt` 的 `@task` 调用 `interrupt`，`AgentRuntime.resume` 用 `Command(resume=...)` 把答案交回原图。正文快照、内容复查、当前运行绑定和批准失效是项目服务自己的职责。磁盘里的 `plan_review` 能解释历史，不能让另一个进程回答已经消失的框架等待。

下面的表放在故事之后，方便查状态和创建入口。正文校验值用来发现内容改变；给模型看的方案提醒只解释当前阶段，不会执行方案或批准工具。

## 查找：正文、批准和工具检查各回答什么

| 想知道什么 | 到哪里找 | 能确认什么 |
|---|---|---|
| 用户实际看过哪份方案 | `FilePlanStore`读取的Markdown，`PlanBackend`提供文件工具访问 | 完整正文，不只有一个“已批准”标记 |
| 目前在规划、自动执行还是完成 | `PlanService`和日志里的`plan_state` | 当前阶段、批准内容的校验值、批准属于哪轮运行 |

## 遇到异常时，程序怎么处理

**Plan 文件还不存在时能批准吗？**

不能凭状态猜正文；review 必须成功读取真实 Markdown，读不到就给出文件错误。

**用户等审批时修改 Plan？**

返回 plan_changed，要求重新审阅；不会把旧 sha256 套到新正文上。

**已批准后模型再写这份 Plan？**

返回 approved_plan_read_only。修改方案要回规划并重新审批，不能一边执行一边改授权内容。

**拿旧 run 的批准开新任务？**

guard 检查 approved_run_id，不匹配就保存 planning，不继承执行权。

**auto 能静默合 worker 吗？**

不能。TeamToolGate 总是绑定 候选源文件内容 与 目标提交 单独审批，Plan的普通自动放行不能代替外层合并审批。

**关闭 TUI 后换 CLI 回答旧 Plan？**

不支持跨进程回答。等待图在内存中；重开会话旧批准也会失效。

**为什么发现文件存在也要写 plan_state？**

document_exists告诉模型和界面方案文件实际是否存在；update_exists 只在变化时追加新状态，避免凭缓存假定文件已写好。


## 面试常见追问

- **Plan 和 Todo 有什么区别？** Todo 是任务列表；Plan 是正文、正文是否改变的校验值，以及这次批准适用哪轮运行。
- **为什么批准后还要每次读 Plan？** 防止外部编辑让执行脱离用户实际审过的快照。
- **为什么只允许一个 Plan 文件？** 让规划期写入例外可以精确表达，避免整个内部目录可写。
- **为什么 ExitPlanMode 是 read 类工具？** 它是规划期必须可调用的控制入口，真实批准仍通过 interrupt。
- **为什么搜索范围在 rg 前限制？** 结果过滤挡不住先扫描其他内部文件；权限必须作用于真实 I/O 范围。
- **为什么 JSONL 记批准却仍让重启过期？** 日志用于解释历史，不替代当前进程里仍保留的执行图。
