# 13　记忆：下一次修代码，怎样还记得用户偏好

上一章已经让“修复 parser.py，并跑测试”成为可重新打开的会话记录。但下周打开另一条会话时，模型不一定会看到今天的聊天。用户想记住的是“解释先给最小例子，Python 测试用 pytest”，不希望每次把整段旧对话重新贴一遍。本章从这个缺口讲起。

```text
本轮用户说明偏好 → 修复完成并保存 run_end
→ 后台读取有限的最近对话 → LangMem提出笔记增删改
→ 检查内容并保存JSON与变更记录
下次任务 → 选择有关笔记 → 把本轮选中的内容写入历史
记错了 → 用户编辑；或撤销最近一次自动整理
```

“保存过聊天”和“保存长期笔记”不是同一件事。记忆模块不会把每句回答永久当规则，也不会把工具日志无限交给后台模型。

## 第一步：新任务开始，先找已有笔记，不凭模型猜偏好

用户再次提交修 parser.py 的请求时，会话先保存这条输入，再调用 `MemoryService.select`。它从应用预先配置的用户、项目两个位置读取笔记，给每条记录附上所属范围与 ID。范围决定它应跟着用户走，还是仅属于这个项目；两个位置刚好有相同 ID，也不能视为同一条。

笔记总数不超过二十条时，服务全部选入。更多时，`ConfiguredMemoryUpdater.select` 把候选分批交给结构化选择链，最后最多取十条。这里是“从已有条目中挑相关内容”，不是要求模型重新写一遍用户画像。选择结果必须是目录里真实存在的 ID；选择调用失败时，服务记录错误，并退回最近更新的十条，让主任务仍能继续。

选中的内容会保存为本轮 `memory_load`，后续构造模型上下文时据此加入笔记。这表示这次到底读了哪些长期内容有迹可查。另一路 `AGENTS.md` 是指令文件：Deep Agents 的 `MemoryMiddleware` 每轮读入允许的文件，再把内容加到每次模型请求的系统提示。项目文件只有在受信任且路径仍在工作区内时才参与；它不经过上述 JSON 笔记选择流程。

## 第二步：这轮明确要求记住，模型通过普通工具修改笔记

用户说“以后都先给最小例子”时，模型也可以主动使用记忆工具。模块提供的不是任意文件写入，而是每个允许范围下的 manage/search 工具：查找用 `create_search_memory_tool`，新增、更新、删除用 `create_manage_memory_tool`。这些是 LangMem 官方工厂，`ScopedMemoryTool` 读取它们真实的参数结构，接进本项目同一套工具声明、权限检查和结果保存流程。

执行器批准一个已声明工具后，`ScopedMemoryTool.execute` 才进入 `MemoryService.tool_operation`。服务再次检查当前会话是否允许记忆操作、是否为主助手、目标范围是否在白名单里；然后拿到本会话修改锁，把记录变化的 store 交给 LangMem。模型拿到的是固定范围的存储接口，不能把参数写成某个磁盘路径去打开别人的文件。

最后写 JSON 前，`JsonMemoryStore` 取得对应文件的修改锁，重读最新版本，检查正文、完整数据大小、数量上限和疑似密钥。实际写成了什么会保留前后值，并在退出操作时记入变更日志。即使磁盘写完后紧接着取消，也不能谎称“什么都没发生”；这些变化稍后要能查清。

## 第三步：聊天已结束，再决定这次有什么值得长期留下

普通用户不一定主动要求调用记忆工具，所以还有自动整理。会话只有在保存完成的 `run_end` 后，才调用 `MemoryService.settled` 预约后台任务；仍在等审批时不触发。历史压缩也可能触发同一路入口，但必须先成功采用摘要，不能把尚未生效的模型草稿当整理依据。

后台任务先准备有限输入：最新摘要最多八千字符，最近用户和助手文本最多四十条、两万四千字符，并保留压缩后仍需要的对话尾部。然后 `ConfiguredMemoryUpdater` 打开独立后台模型，把输入交给 `MemoryConsolidator`，后者直接调用 LangMem 的 `create_memory_store_manager`。新增、合并、删除哪些条目由 LangMem 决定；固定目录、写入检查和实际变更记录仍由项目负责。

这条调用不继承主聊天的思考设置。后台关闭 thinking 和 reasoning_effort，重试次数为零，输入与输出也有限额；主聊天仍使用用户自己的设置。`max_steps=1` 约束整理步骤，不等于保证只发一个 HTTP 请求，模型封装另有最多二十四次调用的边界。服务同时只保留一个未结束的整理任务，关闭会话时等待它退出并关闭后台客户端。

如果整理失败，主任务的“parser.py 已修复、测试结果如下”不会被改成失败。已经完成的笔记变化仍要记录，未写成功的部分也不能假装成功。用户接着发新任务时，第一步的选择流程才会读取当前笔记，而不是盲目相信上轮模型声称记住了。

## 第四步：记错了，撤销的是保存过的变化

假设后台把“本项目用 pytest”误写成所有项目都用 pytest。用户可以先列出笔记，再按用户或项目范围手工修改。`MemoryService.edit` 会明确定位一条记录，走与模型工具相同的存储检查；同一个 ID 在两处都有时，必须指定范围，不能猜应覆盖哪一份。

如果希望直接撤销最近一次自动整理，`undo` 读取变更日志，找到尚未完整撤销的那次整理。恢复前，store 拿齐涉及文件的锁，比较每一条当前值是否仍等于整理结束时的值。若用户后来手工改过其中一条，就拒绝覆盖，说明这次整理之后还发生过修改。撤销恢复保存的原值和原时间，不再次问模型“帮我反向生成”。

检查通过后，每个范围的 JSON 以原子替换方式发布。两个文件并不是一个数据库事务：第二个写失败时，第一个可能已经恢复，所以日志使用 `attempted_undo` 记录实际完成部分；只有整批恢复才记 `undoes`。弄清这条边界后，下一章的 Plan 就更容易理解：长期记住偏好，不等于用户已经批准这次修改方案。

## 框架在刚才的故事里做了什么

这里有三条不能合并的框架路径。Deep Agents 的 `MemoryMiddleware` 只处理允许的 AGENTS 文件；LangMem 的 manage/search 工具供主模型主动读写笔记；`create_memory_store_manager` 供后台从有限对话中整理笔记。它们共享部分存储配置，但触发时间、输入和返回对象不同。

笔记太多时，另有 `ChatPromptTemplate` 与 `with_structured_output(MemoryDirectoryChoices)` 组成的选择链。它仅返回候选 ID 与分数，既不写笔记，也不替代后台 Store Manager。`JsonMemoryStore` 实现框架的 `BaseStore`，使这几条路径能使用同一个受限存储接口；文件锁、原子写、过滤和撤销日志是项目补上的能力。

## 遇到异常时，程序怎么处理

**off 是否把历史笔记删掉？**

不会。off 取消后台任务、写空召回快照，已有 JSON 仍在；clear 才是显式清空操作。

**off时还能显式extract吗？**

可以。AgentSession.memory_extract是用户主动的在线整理入口，不走自动settled的mode检查；仍需配置模型并经过同一存储检查和变更记录流程。

**条目数超过 20 就全部送给主模型吗？**

不会。先走受控选择，再最多注入 10 条；选择失败有明确降级和审计。

**后台抛异常会让用户本轮失败吗？**

不会。consolidate 捕获并记录后台异常；取消仍传给负责等待该任务的对象，让关闭过程等它真正停止。

**自动整理写了一半失败怎么办？**

已写入的变化仍记录；不把整轮说成没有发生，用户可以查看日志并撤销可核实状态。

**撤销跨两个 JSON 是一个事务吗？**

不是。先拿齐各文件的锁并完成比较，但之后每个JSON分别替换；后一个磁盘写失败可能留下部分恢复。

**同一 memory_id 在两个作用域都有怎么办？**

手动命令用`--scope user`或`--scope project`说明要改哪一处，不能猜测覆盖哪一条。

**为什么保留 migration 字段却删除迁移服务？**

旧JSON仍可按当前数据格式读取，不等于仍提供旧迁移流程；无关旧字段会在后续写入时丢弃。


## 面试常见追问

- **为什么不把 AGENTS.md 也写入 JSONL？** 框架处理器每轮读入一次内部状态，再加到各次系统提示；不反复读盘，也不被压缩清掉。
- **LangMem 和 pycode 各负责什么？** LangMem 决定条目内容和合并；pycode 控制文件、时机、过滤、日志与撤销。
- **为什么不盲重试后台整理？** 一次流程可能已写部分状态；这里选择零重试、可审计，而不是隐式重复修改。
- **为什么需要两层锁？** 服务锁防本会话的工具、后台和手工操作同时修改；文件锁防不同会话相互覆盖JSON更新。
- **为什么 undo 要比较 after？** 保护之后的用户修改；当前值不匹配时宁可拒绝，也不能还原成旧值。
- **怎么避免隐藏密钥藏进 metadata？** 检查完整序列化 value 与递归原始字符串，不能只检查界面显示正文。
