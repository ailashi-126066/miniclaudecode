# 12　会话：修到一半退出，下一次怎么接着做

上一章的 Hook 解释了运行前后可以插入什么动作。本章先把那些动作放下，只跟着用户的一次操作走：**“修复 parser.py，并跑测试。”** 用户真正关心的是这句话有没有保存、执行停在哪里，以及取消后再次打开会不会重复改文件。

```text
打开上次会话 → 输入“修复 parser.py，并跑测试” → 保存用户消息
→ 启动本轮执行 → 请求运行测试的审批 → 等用户回答
→ 同进程回答后继续；或者取消，再检查已修改文件
→ 保存本轮结果 → 下次打开时展示旧记录，开始新的任务
```

这里有两件容易混在一起的事：对话记录可以存到磁盘，正在等待审批的执行过程却只留在当前进程。下文每一步都会说明自己处理的是哪一件。

## 第一步：打开旧会话，先解释昨天留下了什么

假设昨天的运行在修改 parser.py 后被关掉了。应用通过 `open_agent_session` 打开同一份会话日志，并取得写入这份日志的资格。此时还不能立即请求模型，因为最后一个工具也许已经改了文件，却没来得及保存结果；直接接着跑可能把修改再做一次。

因此打开过程先调用 `recover_conversation`。它把助手发出的工具调用与已经保存的工具结果配对：有完整结果的保留，无法确认的补成 `tool_interrupted`，意思是“不能确认这个工具是否完成”，而不是“工具肯定没执行”。旧运行尚未消费的补充输入也会留下过期提示。这个函数整理日志，不调用昨天的 Bash 或文件工具。

打开成功以后，界面可以重新展示已有历史。用户需要结合文件现状决定下一步，例如重新发出“检查 parser.py 目前的修改，再跑测试”。这才是一轮新任务；磁盘日志不会凭一个旧的批准答案复活昨天的执行图。取消和关闭也在下方同组入口展开，便于比较它们与启动恢复各自做什么。

## 第二步：这句话先保存，再交给真正的模型循环

用户提交请求后，`AgentSession.run` 先确认消息来自用户、带有唯一 ID，而且同一会话没有另一项操作占着执行位置。随后 `_run_locked` 保存这条用户消息，再召回这次可能需要的记忆、选择模型、更新 Skill 列表。这样即使下一步连不上模型，用户说过什么仍有记录。

同一个消息 ID 再次到达时，服务会比较正文和当前分支。完全相同且已经结束的输入可以返回已保存的结果；内容变了或者属于别的分支，就明确拒绝。这里做的是识别重复提交，不是给修改文件的工具提供一个随便重试的开关。准备完成后，服务写下 `run_start`，为这轮执行分配 `run_id`，后面的工具结果才知道自己属于哪一次任务。

接着 `ConfiguredRuntimeLauncher` 找到刚保存的运行身份，通过应用组装时传入的工厂取得本轮容器。容器中的 `AgentRuntime.run` 创建 Deep Agents 图，最终 `graph.ainvoke` 才开始请求模型、执行工具。会话服务没有另写一个模型循环。图执行期间，框架会调用 `HistoryMiddleware` 保存完整回复；这不是 launcher 返回以后才按章节顺序调用的函数。

工具已经保存结果时，会先把消息写进日志，再关联完整输出和文件快照，最后通知界面。整轮返回会话服务后，`record_run_result` 才决定记录“等待输入”还是“本轮结束”。因此屏幕出现了流式文字，不能直接推导为这段回复已完整保存。

## 第三步：测试需要批准时，继续的是当前那次执行

模型读完代码、提出运行 pytest 后，权限检查可能要求用户确认。LangGraph 暂停图并返回待回答问题；会话把问题和当前检查点写成 `run_wait`。launcher 此时保留原容器，让同一进程里的 TUI 可以回答；它不会因为一次等待就关闭连接并新建另一个任务。

用户选择批准后，`AgentSession.resume` 找到当前还未结束的运行，先保存这次回答发生过，再把答案交给 launcher。`AgentRuntime.resume` 读取活图中的问题，核对问题 ID、操作 ID和答案形状，然后用 `Command(resume=...)` 交回 LangGraph。答错格式时仍保留等待，不会偷偷替用户选择批准。

恢复后的工具依然要核对这次操作的实际内容，不能把一个旧答案当成对任何测试命令的许可。图结束后，恢复入口也回到与新任务相同的结果保存函数。若进程已退出，launcher 找不到原容器就报告 `run_expired`；日志可以解释当时在等什么，却不能代替那张内存中的图。

## 第五步：想回看、撤改动或缩短上下文，分别找哪个入口

测试结束后，用户可能想从旧消息另开一条思路。`branch` 改的是日志当前指向哪一个历史节点，不会把 parser.py 一起变回去。切换后重新初始化 Plan，是因为旧分支的批准不能自动适用于新分支。原消息正文一直保留，分支只是选择接下来沿哪条历史继续。

如果用户真的要撤回代码，先调用 `preview_revert`，明确只回退对话、只恢复文件，还是两者都做。预览把将改哪些文件、预期当前版本是什么列出来；确认后 `revert` 才执行恢复。缺少可核实的文件快照时，不能仅靠一句“撤销上次修改”猜原文件内容。

还有一种需求是“对话太长了”。`compact` 不回退代码，也不重跑修复任务，而是准备本轮真实工具信息，生成并验证一份历史摘要。摘要被采用后，旧消息仍在原日志里，只是后续模型不必每次读取整段；这时才通知记忆模块可能需要整理长期偏好。下一章就顺着这个通知，说明它怎样让下次任务记住“先给例子，再解释”。

## 框架在刚才的故事里做了什么

`AgentRuntime.build` 把文件后端、按顺序排列的 middleware、运行上下文类型和 `InMemorySaver` 交给 `create_deep_agent`。Deep Agents 与 LangGraph 负责模型和工具如何轮流执行、何处暂停、如何把恢复答案送回去；launcher 负责保留或关闭那次执行使用的容器。这是两个对象合作，不是两套执行循环。

`HistoryMiddleware.abefore_model`、`awrap_model_call`、`aafter_agent` 是框架在相应时点触发的回调：分别准备本次请求、保存完整助手回复、处理结束前输入。磁盘 JSONL、重复输入识别、旧运行整理、分支与资源关闭则由项目自己补充，框架的内存检查点没有替项目提供跨进程续跑。

下面的表格是读完故事后的查找索引。遇到“谁创建、谁使用、谁关闭”的问题，可对照组装表回到相应步骤；每一行都说明该对象什么时候交给下一步，以及谁负责在成功、失败和取消时等待它结束。

## 遇到异常时，程序怎么处理

**同一个 input_id 换了内容？**

返回 input_id_conflict。存储里的旧身份不能被新正文覆盖。

**从另一条分支拿来旧输入 ID？**

返回 input_branch_conflict。历史重读只对当前活动分支成立。

**进程重启后为什么不能提交昨天的 approve？**

内存中的 graph 已不存在；JSONL能说明之前发生过什么，但不能让新进程继续原来的图。

**排队后立即取消，会丢掉用户补充吗？**

input_queued 已落盘；恢复把未消费输入变成 input_expired 提示，不伪装成已响应。

**run 已结束却还有消息到达？**

持久输入队列拒绝旧运行的新输入；Team inbox 会把处理中的消息退回待送，不假装已送达。

**展示出错会损坏会话吗？**

SessionView和UI只读取并展示记录；原始 JSONL 不随展示失败重写，重新打开可重建视图。

**回退对话会自动回退文件吗？**

不会。RevertPlan 的 dialogue／code／both 模式分别表达范围，先预览再确认，文件恢复有自己的事务记录。


## 面试常见追问

- **为什么会话服务还需要 launcher？** 会话保存任务记录，launcher保留活图并关闭执行资源；它们结束的时机不同。
- **为什么 user 消息会 append 两次？** 上层先保存用户输入，runtime也可被独立调用；存储按同 ID 同内容去重。
- **为什么不用数据库 checkpoint 自动续跑？** 当前选择内存等待，重启只整理未知结果，避免重复命令与旧审批复用。
- **锁解决了什么？** 会话执行锁防止两项命令同时改变会话；writer.lock防止两个进程同时写日志；输入锁使排队提交与结束判断不能互相错过。
- **完成事件能先发吗？** 不能。先保存工具结果、关联完整输出和文件记录，完成通知在后。
- **怎么证明恢复没有重跑？** 查看 recover_conversation：它扫描日志、补未知工具结果并记录旧运行结束，没有调用旧工具执行器。

用户的修复任务已经能被保存、停止和重新查看，但新会话不一定读到旧聊天。接着读[长期记忆](13-memory.md)，看“下次也先给最小例子”怎样从这轮对话变成另一轮真正可用的笔记。
