# 02　程序先怎样记住：用户让它修 parser.py 并跑测试

上一章已经把命令行、配置和功能模块连成了应用，也打开了会话。现在用户发来一句话：“修复 parser.py，并运行测试确认。”这里的 parser.py 是用户工作区中的示例文件，不是让程序修改自己的命令行解析器。

此时先别急着找调用模型的代码。程序马上要处理几个更基础的问题：这句话有没有保存？模型以后看到的是哪一条分支？修改文件时用户按了停止，能不能说文件一定没改？屏幕上的文字和磁盘历史又是什么关系？这四个问题会反复出现在后面的模型、工具和界面流程里。

本章顺着这件事走四步。`kernel`这个目录名指的是大家共用的数据格式和基础方法，不表示这里负责整个Agent的业务调度。先看它们怎样解决眼前的问题，再在末尾回看目录分工。

## 第一步：先把“修复并测试”保存成一条完整消息

应用收到文本后，把它放进`Message`，同时给出消息ID和`role="user"`。消息ID不是展示用的序号：如果调用方重送同一个ID，存储层要判断它是不是同一份内容，不能把“再读一次已完成结果”误变成“重新修改一次文件”。具体去重在会话存储中实现，这里先看大家约定传递什么。

`Message.text`保存这句需求。后续模型提出读文件，会在另一条assistant消息里保存`tool_calls`；工具真正返回后，再保存带`tool_result`的消息。它们采用同一个消息格式，但代表不同阶段。因此，一段尚未结束的模型输出不能直接填成“工具已经执行成功”的结果。

这样做的直接好处是，后面各模块不用分别猜测对方的字典长什么样。模型转换方法能读取工具调用，历史显示能读取正文，预算方法能读取模型实际返回的用量。`Message`里没有官方SDK的`AIMessage`等对象，读取历史的功能也就不必为了这句话加载某家模型SDK。等真正发送请求时，下一章才会转换格式。

保存后还有一个不明显的问题：`Message`虽然是不能重新赋值的dataclass，它的`provider_metadata`等字段里仍可能装着字典。假如界面为了显示方便修改了那个字典，历史也跟着变了，消息ID就不再对应固定内容。所以存储方法会用`freeze_value`递归处理字典、列表和dataclass内部的值。只读历史可以被很多地方共用；确实要交给可修改的外部代码时，再用`clone_value`做副本。

现在程序能把需求保存下来，也能把后续消息保持为不会被界面意外改动的记录。但“保存了所有消息”还没有回答另一个问题：当前这次任务究竟应该接着哪段历史继续？

## 第二步：从所有记录中，取出用户当前选择的那一条历史

假设用户第一次修复后发现方向不对，切回修改前的位置，再要求用另一种办法。磁盘里会同时保留两条路线。如果程序只拿日志最后几行，模型就可能读到用户已经放弃的修改，甚至把另一条路线的测试结果当作当前结果。

为避免这个问题，快照`SessionSnapshot`分别提供全部记录`entries`和当前选择的位置`leaf_id`。每条记录有`parent_id`，表示它接在哪一条后面。`SessionTree`接收这批记录或存储已经检查过的索引，`path(leaf_id)`再沿父节点往前找，最后返回从最初记录到当前选中位置、按发生顺序排列的记录。

阅读下面的代码时，先看构造函数怎样拒绝空ID、重复ID和还没出现的父节点，再看`path`怎样倒着回溯、反转结果。`path`并不替用户决定选哪条分支；传入未知叶节点会明确失败。已经由存储验证过的Mapping索引可以直接复用，这样每次展示几千条消息时不用重新建一遍索引。

## 第三步：保存或修改文件时，停止不等于回滚

前两步已经让程序知道需求和当前历史。先暂停模型部分，看看这次任务以后必然会碰到的文件写入。保存会话记录要写磁盘，真正修复parser.py也要写磁盘。如果用户在写入途中按停止，异步函数可以收到取消，但已经交给线程的文件操作不会因此自动消失。

`owned_io(function, *arguments)`处理的是这个等待关系。调用方先检查文件路径和允许范围，再把具体I/O方法交给它。它在线程里执行该方法，外部取消到来时仍等待线程完成，然后才把取消继续向上传。于是上层能够诚实地告诉用户“执行已停止，刚才开始的写入已有结果”，而不是错误地声称“既然取消了，文件一定没变”。

写入完整JSON等单个文件时，`atomic_write`先把全部字节写到同目录的临时文件，刷新并`fsync`，再用`os.replace`发布目标。它避免读者看到半份内容，但不负责阻止两个写者互相覆盖。需要单写者时，调用方还会用`FileLease`取得平台文件锁。下面展示这三个方法如何由调用方组合；它们不是彼此硬编码调用的一套万能事务。

## 第四步：先有可引用的记录，再告诉界面“完成了”

修复任务执行时，用户当然不想只看到一片空白。程序会不断发出模型文字、工具进度和完成通知。但如果先显示“测试已完成”，随后才尝试保存测试结果，一旦保存失败，用户看到的成功就没有依据了。

因此，负责工具结算的代码先保存完成消息并绑定完整输出，再调用`EventStream.emit`发布事件。`EventStream`接收的是事件种类、数据和可选操作ID；它只负责顺序投递，不负责把工具消息写进历史。这里要区分调用方保证的“先保存”和发布器保证的“按顺序送”。

发布器持有一个锁。配置了事件记录方法时，它先取得本次事件序号；随后给每个消费者传递独立副本。默认的`MemoryEventJournal`只是在内存里保存有限数量事件，并按会话和每次运行分别计数。程序重启后这个环为空是正常的，历史仍要从JSONL读取，而不是把事件环当成第二份恢复日志。

## 走完后再看：为什么这些代码不直接使用Agent框架

这四步用到了Python的dataclass、不可变映射、异步锁、线程等待、平台文件锁和原子替换。它们没有调用模型，也没有让LangGraph决定哪条历史有效。原因来自刚才的例子：无论模型来自哪家SDK，无论用户从CLI还是TUI进入，消息格式、分支关系和磁盘完成状态都应该相同。

因此kernel没有单独的`module.py`装配入口。应用把`EventStream`接到消费者，把`SystemTiming`等实现交给需要时钟的方法；存储模块显式使用`kernel.adapters`中的文件能力。它们创建了什么资源，就要在相应操作完成时释放，不能因为叫“共享基础设施”就变成无人关闭的全局对象。

| 回看刚才遇到的名字 | 它在例子里回答的问题 |
|---|---|
| Message / ToolSpec | 保存什么消息、向模型说明什么工具；声明本身不批准执行 |
| SessionSnapshot / SessionTree | 当前选择哪条历史，如何取出它 |
| freeze_value / clone_value | 哪些内部值可以共用，何时必须做可改副本 |
| FileLease / owned_io / atomic_write | 谁可写、取消时等谁、单个文件怎样完整发布 |
| EventStream / MemoryEventJournal | 怎样依次通知界面，哪些事件只存在本进程 |

## 读懂检查：把问题带回parser.py任务

- **用户切回旧分支后，为什么不能只取日志最后十行？** 因为当前叶节点和日志追加顺序不是一回事，要沿每条记录的父节点取出选中的路线。
- **界面收到完成事件，能否用它代替工具结果？** 不能。事件只负责显示，保存结果和输出引用发生在调用emit之前。
- **用户取消时，owned_io为什么不立刻返回？** 因为线程可能已经在写parser.py或会话文件，必须等自己开始的操作有明确结果。
- **原子写是否保证多文件一起回滚？** 不保证，它只发布一个文件；业务记录、版本比较和多文件恢复仍要各自实现。
- **冻结dataclass为什么还处理内部字典？** 顶层不能重新赋值，不代表字典内容不可变；不递归保护内部值，就会让显示代码改到历史。

这些答案说明程序已经能够可靠地传递“发生了什么”。但到现在还缺少能读懂需求、决定下一步的模型。下一章从应用已经选好的Provider开始，跟着第一次请求，看密钥何时读取、网络调用之前记什么、失败以后又怎样处理。
