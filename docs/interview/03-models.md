# 03　把“修 parser.py”真正交给模型

上一章留下了一条有ID的用户需求，以及当前分支上应继续阅读的历史。它们仍是项目自己的`Message`，模型SDK还没有收到请求。现在应用需要把这段历史交给选定模型，让它决定先读parser.py，还是先查看已有测试。

这一章不从一张类名表开始。我们跟着这次请求走四步：准备可关闭的SDK对象，确认这次模型能看到哪些工具，保存请求并发送，最后处理暂时失败或备用模型。Agent框架何时回调这些方法，第05章会把它们接起来。

## 第一步：选好了Provider，为什么还不能直接发送文本

上一章的应用配置已经选定Provider。这个配置说明模型名、API地址、输入窗口、输出预留和密钥引用，却不是已经打开的连接。为了发出请求，应用调用`await ModelsModule.owner(...)`，传入Provider、本会话和本次运行的ID，以及请求用途。

方法名里的`owner`可以直接理解为“这组对象最后由谁负责关闭”。它返回的`MeteredModelOwner`把SDK模型、请求记录方法、SQLite连接和可能自建的事件记录放在一起。一轮Agent运行中可能多次请求模型，不是每发一个token就重建这组对象；这轮不再需要它时，调用者统一等待`aclose()`。

在构造过程中，`ModelsModule.credentials`才解析当次Provider引用的密钥。默认情况下它调用应用预先交进来的凭据方法，从环境或授权的.env补齐缺失值。目录适配器和SDK可以在运行内存中持有凭据，但缓存文件与历史不写真实密钥。这也解释了上一章为什么组装应用时不必立即读取全部凭据。

## 第二步：先决定这次模型能看见哪些工具

用户要求修改并测试，不代表模型应该看到程序中所有可能安装的工具。请求里通常有读写文件、Bash、Plan控制工具；如果用户加载了Skill，后面还可能增加Python资源；启用了MCP，也可能增加远端工具。目录里存在一个名字，不等于这次模型已经看到了它的参数说明。

Agent会在发送前把当前请求交给`ToolSelector.select`。工具不多或选择器关闭时，方法直接保留请求；候选数量或说明体积达到阈值时，才调用官方`LLMToolSelectorMiddleware`缩小集合。文件读取等必须保留的名称由应用和相应模块给出，Models不在内部猜哪些名字属于Skill或MCP。

选择器返回后，调用流程才接着执行`calibrate_model_request`。这不是选择器内部又去调用一遍校准，而是Agent组合的下一步。它遍历最终`request.tools`，还原每个工具的真实说明，把这些名称保存到`context.selected_tool_names`，同时计算系统提示和工具说明是否变化。

## 第三步：先记下要发的一次请求，再等待模型回答

请求进入`model_request_step`时，这个函数本身只是把方法包装成一个可组合步骤。代码用的是LangChain的`RunnableLambda`；只有随后调用这个步骤的`ainvoke`，内部闭包才会把请求交给`ModelRequestRunner.invoke`。读代码时不要把“创建步骤”和“已经发请求”混成一个时点。

Runner先拿锁，避免同一组SDK观察状态被内部并发请求覆盖。进入一次实际发送前，它创建`RequestRecord(status="started")`并写入SQLite。记录里既有会话和运行ID，也有这次逻辑请求的`logical_id`，以及实际尝试序号`attempt`。网络请求必须排在这次写入之后；账本写失败，就不能继续悄悄付费请求。

然后才调用框架传来的模型`handler`。SDK负责真正的协议交互，`ProviderObservation`观察SDK已经解码的响应，补充模型实际返回的用量和响应身份；没有返回的用量仍记为未知。完整响应返回后，Runner把记录改成已完成，保存Provider实际报告的token数量，再通知界面更新用量、结束本次请求。代码中的状态值是`completed`。还没结束的token片段由界面显示，不在这里伪造成一条已完成assistant消息。

## 第四步：主模型真的不可用时，才考虑备用模型

`ModelFallback.invoke`先让主模型自己的Runner处理请求。主模型成功就直接返回，不构造候选。如果它报的是允许切换的Provider故障，才解析备用配置、检查能力并按需创建另一组模型对象。磁盘写失败、工具说明变化或编程错误不会因为换个模型就自动消失，所以这些错误必须停止流程。

为什么要再检查能力？因为当前请求可能包含工具、图片或Provider专用工具字典，而备用模型不一定支持。不能把用户的parser.py任务换到另一个模型后，继续沿用主模型的工具或容量判断。代码会给不兼容候选记skipped，并让真正要执行的候选重新整理消息、校准工具和预算。

## 回看这次请求：模块入口和框架各做了哪部分

应用最开始创建`ModelsModule`时，给的是文件路径、时钟和“以后需要时怎样取得密钥”的方法。真正开始一轮运行才调用`owner`；需要工具选择、摘要或记忆整理时，也通过各自异步工厂建立模型对象，并记录不同用途。`scoped`只为子工作区替换请求数据库路径，保留已经选好的模块类型和凭据来源。

SDK构造和协议差异在`ModelFactory`中；官方重试、备用模型、工具选择机制分别由对应中间件提供。项目增加的是实际请求前后的记录、错误分类、最终工具名单与“谁来关闭客户端”。所以这些框架类不是一个额外执行器名单，而是刚才四步中各解决一件具体问题。

| 现在回查代码 | 在故事中的位置 | 完成后交给谁 |
|---|---|---|
| ModelsModule.owner / ModelFactory.create | 请求之前准备SDK与账本 | 当前运行负责最后aclose |
| ToolSelector / calibration | 发送前确认工具集合和大小 | 模型请求，以及之后的执行检查 |
| ModelRequestRunner | 先保存开始记录，再发送，最后保存完成或失败 | Agent的完成响应保存方法 |
| ModelFallback | 仅在允许失败后检查候选 | 同一业务请求继续，账本保留候选位置 |
| MeteredChatModel | 选择器、摘要、记忆等组件也要请求模型时 | 仍进入同一计费方法，不执行工具循环 |

缓存`model-catalog.json`只保存模型身份与能力。实际尝试保存在SQLite的`model_requests`；JSONL中的工具集合和候选说明用于解释当时怎样执行，两者回答的问题不同。网络等待期间不持有一笔长SQLite事务。

## 读懂检查：如果这次修复请求出了问题

- **为什么关闭SDK内置重试，却仍能重试503？** 因为官方重试中间件重新调用Runner，每次实际请求都能单独记录。
- **logical_id和request_id为什么不能只留一个？** 一个标识模型轮次，另一个标识实际付费尝试；失败后再试仍是同轮，但不是同次请求。
- **选择器不开，为什么还要校准？** 最终工具名称和输入大小仍要绑定到真实请求，不能仅凭目录中有实现就允许执行。
- **备用模型为什么重新看工具和预算？** 它的能力与窗口可能不同，不能接过请求就照搬主模型条件。
- **后台模型为什么有单独用途和关闭方法？** 选择工具、写摘要与整理记忆都可能付费，不能混进主回复后丢掉请求或连接。
- **模型没返回用量，能否用估算补上账单？** 不能。估算供下一章判断容量，Models保留Provider已报告或明确未知的计费信息。

现在可以把问题从“这次模型请求有没有被正确发送和记录”，移到“模型下一次应该读到什么”。当读文件与测试结果不断增加，Context负责保留正确路线、解释容量，并在不丢原始记录的前提下缩短发送内容。
