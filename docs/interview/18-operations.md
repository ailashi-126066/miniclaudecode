# 18　跑不起来或数据太多时，从哪里开始检查

假设前面的修复任务没能开始：程序提示找不到rg，或者文件快照不可用。此时继续追模型怎么调用工具，往往找错了方向。先需要确认这台机器、工作目录和本地数据是否准备好。

这一章顺着实际排查来读。先用doctor看环境，再看程序怎样清点和清理自己管理的数据，最后说明交付前怎样验证安装包。它们是不同操作，不应因为一个通过就把其他检查也算通过。

## 第一步：先看程序在哪里运行，缺了什么

`pycode doctor --json`不需要模型配置。CLI进入doctor分支后，会分别读取应用状态、沙箱状态，以及rg、git、bash等工具在PATH中的位置，再组合成输出。

为什么要分开读？工作区存在，不代表Git快照一定可用；有bash，也不代表当前平台具备macOS那样的沙箱。输出里保留每项结果，用户才能知道缺的是哪项能力。

应用状态通过 `Application.status`取得。它让会话模块创建 `ApplicationService`，再由后者调用工作区检查方法。这样，CLI和TUI查看的是同一套状态，而不是各自写一遍“项目是否存在”的判断。

外部工具由 `external_tools`用 `shutil.which`查找。找不到rg时会给用途和安装提示，不会替用户执行安装。doctor的返回码最终还要看工作区是否存在，不能把它简单解释为“所有功能全部就绪”。

## 第二步：知道程序数据放在哪里，才能判断能否清理

修复任务会留下会话历史、模型请求记录、工具输出、摘要和快照。程序把这些数据放在用户数据目录中，按工作区分组，而不是把所有项目都塞进同一个会话文件夹。

`StorageLayout`先把工作区路径规范化，再计算一串内容摘要，取前24位作为项目目录名。这里使用完整路径，是为了让两个都叫project的文件夹也能分开；后续的sessions和runtime.sqlite都放在对应项目下面。

这一步只确定存放位置，不判断某个输出能不能删。一个文件看起来很旧，也可能仍被历史消息、摘要或回退记录引用。下一步必须先把这些关系查清楚。

<div class="reading-step"><p class="reading-guide" data-call-guide="src/pycode/session/adapters/storage/layout.py::StorageLayout">同一台机器可能有两个都叫project的目录，所以打开应用时先让StorageLayout根据完整路径确定项目数据目录。它把规范后的路径变成稳定名称，再给出sessions和runtime.sqlite的位置。后面的历史和请求记录沿这些路径保存，清理也知道自己管理哪份数据。</p><details class="call-node" data-function="src/pycode/session/adapters/storage/layout.py::StorageLayout"><summary><span class="call-label"><strong>从完整工作区路径确定数据存放位置</strong><span class="call-signature">StorageLayout</span><span class="call-file">src/pycode/session/adapters/storage/layout.py</span></span><span class="call-toggle" aria-hidden="true"></span></summary><div class="call-body"><ol><li>使用完整规范路径计算摘要，不只取最后一层目录名。</li><li>这个类确定位置，不判断某份文件是否仍被使用；引用与清理要交给后面的服务。</li></ol><p class="call-code-caption">完整定义 · 源码 L8–L14</p><pre><code class="language-python">class StorageLayout:&#10;    def __init__(self, workspace: Path, user_data: Path) -&gt; None:&#10;        normalized = os.path.normcase(str(workspace.resolve()))&#10;        key = hashlib.sha256(normalized.encode()).hexdigest()[:24]&#10;        self.project = user_data / &quot;projects&quot; / key&#10;        self.sessions = self.project / &quot;sessions&quot;&#10;        self.runtime_database = self.project / &quot;runtime.sqlite&quot;</code></pre></div></details></div>

## 第三步：先找仍在使用的数据，再决定哪些能处理

`storage status`只统计程序管理的数据。`storage gc --dry-run`则进一步列出拟处理的动作；gc在这里就是清理不再使用的数据，不是让用户对着目录手动删文件。

CLI先通过 `Application.storage`取得 `StorageGC`，再调用collect。collect让文件适配器清点对象，这里的“对象”是一个输出、一份摘要、一条会话或一个快照等受管理数据。然后 `mark_objects`从需要保留的起点出发，沿引用找到仍然需要的数据。

有了这份结果，才逐项决定：受保护或仍被使用的保留；没有引用的先移到可恢复的位置；已经移走、到保留期且仍无引用的，才考虑彻底删除。当前保留期是30天。执行具体文件动作时还会再检查当时的条件，不能只相信较早那次清点。

`dry_run=True`只返回决定，不调用真正移动或删除文件的方法。真实执行则逐项审计：失败也会记下结果和错误类型，再把异常抛回去，不能把未完成部分报告成成功。这里的临时移走是存储管理动作，和限制命令权限的进程沙箱不是同一件事。

## 第四步：开发机能跑以后，还要看安装包能否独立运行

前几步说明本机环境和数据。准备交付时，还需要另做三类检查：源码组织是否符合约定、构建后的包是否能在新环境使用，以及平台沙箱是否真的挡住了越界操作。

架构脚本先解析源码导入和定义，检查模块依赖、公开入口与实现对照。它能发现例如app又堆回旧入口、功能直接引用另一功能内部实现等问题，但没有运行用户任务，不能据此判断运行效果。

`verify_release.py`会构建wheel和sdist，再检查内容和入口，创建新的venv安装wheel。新环境会去掉开发机的PYTHONPATH/PYTHONHOME影响，再运行版本、doctor、help及最小本地模拟模型会话。这样才能知道安装包自身是否包含该有的文件，而不只是开发目录里的src能运行。

最后，`verify_seatbelt.py`在macOS上实际测试允许的工作区写入、越界写入、私有目录读取和网络开关。它的结论限定在这些真实向量和平台，不能替Linux或Windows承诺同样的物理隔离。

下面是三个独立脚本入口。它们并不是doctor每次都会依次调用的函数。

## 回头看，框架和标准库分别帮了什么

doctor和storage这些命令通过argparse解析参数，再用asyncio等待产品提供的应用方法。它们不需要为了查看本地状态而创建一张deepagents图，也不必连接模型。

StorageGC只负责先读清单、判断引用，再请求文件适配器执行动作；文件的读取、移动、锁和审计在适配器中完成。这种分工让清理规则可以按数据关系解释，而不是藏在一段遍历目录的代码里。

发行脚本使用subprocess调用ruff、build、venv和pip。最小模型会话连接的是本地测试服务，验证安装和框架接线；真实DeepSeek验收是另一件需要明确授权的事。

## 这些检查怎样接到应用里

doctor调用 `compose_application(config).status()`和`sandbox_status()`；storage调用同一Application的`storage()`。前者取得本地检查结果，后者取得能读管理清单、处理受管理数据的服务。两者都沿用程序已有模块，不在CLI里再建一套文件操作。

维护脚本通过产品公开入口做最小运行检查。文件系统、模型和UI的具体创建仍由各自模块完成，脚本只安排验证步骤并保存结果。

| 你要查的动作 | 从哪里进入 | 去哪里看实际处理 |
|---|---|---|
| 检查工作区和工具 | CLI的doctor分支 | ApplicationService、external_tools、沙箱状态 |
| 查看本地数据数量 | storage status | StorageGC.status与文件清点 |
| 预览或执行清理 | storage gc | StorageGC.collect与FileStorageObjects |
| 检查源码组织 | check_architecture.py | 各项静态规则和真实定义 |
| 检查安装包 | verify_release.py | 每项子命令及新环境结果 |
| 检查macOS隔离 | verify_seatbelt.py | 实际命令的退出码与输出 |

## 遇到失败时，顺着刚才的步骤判断

**没有git，是否所有操作都不能用？** 不一定。Git快照和worker需要它；其他功能按自己的依赖判断。doctor会报告具体缺项，不替不存在的快照制造版本。

**数据已经移到暂存区，为什么又被恢复？** 如果新的引用表明它仍被使用，清理时应该保留或恢复；“以前没引用”不能覆盖现在的需要。

**记忆文件会被当作没有会话引用的垃圾吗？** 当前清点逻辑显式保护记忆目录，不能仅因某份笔记没有出现在当前会话就删除。

**为什么发行报告还存源码摘要？** `source_digest`核对src、pyproject.toml、requirements-dev.lock和docs/licenses这份清单，防止验证过程中这些输入变化后混用结果。它不覆盖scripts、evals、tests等任意仓库修改，不能把保证扩大。

**本地检查通过，等于已经上线吗？** 不等于。它们解释本机能力、对应安装包和相应平台向量；线上容量、部署和长期运行是另外的验证工作。
