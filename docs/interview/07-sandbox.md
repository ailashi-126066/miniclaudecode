# 07　测试命令怎样启动，又怎样被可靠地停止

上一章中，模型改完 `parser.py`，准备调用 `Bash("python -m pytest -q")`。工具执行器已经检查了参数和权限，但“允许执行”还没有回答两个问题：这个进程能读写机器上的哪些位置，用户取消时又怎样确保它真的停了？

先分开这两件事会更容易理解后面的函数。批准决定这一次能不能运行；操作系统沙箱限制获准的进程能做什么。把工作目录设成项目目录，只能改变相对路径的起点，不能阻止命令使用另一个绝对路径。

## 第一步：先查这台机器到底能提供什么限制

打开界面或运行doctor时，`Application.sandbox_status`会通过 `SandboxModule.backend` 选择当前平台实现。在macOS上选择 `SeatbeltSandbox`，其他平台返回明确的不可用状态。这里还没有执行测试，也没有调用模型。

Seatbelt不能只靠“文件存在”判断可用，所以 `status` 会进入 `usable`，实际运行一次 `sandbox-exec ... /usr/bin/true`。它等退出码，限制两秒；取消或超时也要清理这个短进程。这样界面显示的available来自真实探测，而不是从配置里猜出来。

配置里的 `off` 表示不加这层OS限制，普通权限检查仍在；`on` 表示在支持的后端启用隔离，但不自动批准命令；`on-auto` 才允许少量明确的只读命令跳过人工批准，而且仍要在可用沙箱内运行。测试命令并不会因为名字里出现python就被当成只读。普通主会话在不支持OS隔离的平台仍使用权限审批，不能声称已有同等的文件限制；严格worker会拒绝执行。

## 第二步：Bash把获准的测试调用变成实际启动参数

现在轮到 `Bash.execute`。它接到的是执行器已经检查过的 `command`、`timeout` 和当前工作区。函数先构造明确的参数列表：Bash可执行文件、`-c`、命令文本，再调用 `sandbox.launch`。

`launch` 在启用隔离时会重新检查可用性。原因是启动界面时可用，不代表过了十分钟仍可用。如果现在失败，就报 `sandbox_unavailable`；不能把用户批准的隔离命令偷偷换成裸命令。检查通过后，它用 `build_profile` 生成规则，将规则和原来的argv一起交给 `sandbox-exec`。

规则从默认拒绝开始，按程序启动需要开放系统目录和Python导入路径，再允许工作区读写。工作区中的 `.git`、`.pycode`、真实dotenv文件仍受保护；HOME下的常见凭据目录也不因“允许项目读写”而开放。能安全表达规则时，只对工作区的 `.env.example`模板文件有限放行，不因此打开真实 `.env`。网络是否可用由单独的配置决定。

Bash的timeout输入范围是0.1～600秒，默认120秒。随后它创建输出writer，并重新构造子进程环境。`subprocess_environment`只保留PATH、语言、临时目录等运行所需变量；凭据型变量即使在父进程中存在，也不会默认传给测试。普通额外变量可以显式配置，但密钥、token等名称不能借这个选项透传。

这条环境规则不能替代文件隔离：`off`时，命令仍可能尝试读取磁盘上的文件；能不能读到它，取决于OS权限和是否启用沙箱。

## 第三步：启动以后，一边收输出，一边保留停止它的能力

`Bash.execute`把argv、工作区、writer和超时交给共享的 `run_process`。这个函数也用于Python Skill和command Hook，因此所有这些命令都能使用同一套超时、输出和取消处理。

进程创建本身也是一个会等待的操作。程序可能已经创建了子进程，Python协程却正好收到取消。如果直接结束协程，就可能丢掉新进程。`run_process`因此保存创建任务，在取消时也先等到真正的进程对象，再把它停止。

进程启动后，标准输出和标准错误合并到一条管道。读取任务（reader）不断读64KiB字节，写进上一章的输出writer；需要实时显示时，再用增量UTF-8解码把片段交给进度回调。它不能等测试结束以后才开始读，否则大量输出可能把管道堵住。

两秒超时，或用户按取消时，`stop_process`负责停止整组进程。POSIX使用独立session加 `killpg`；Windows用Job或树级结束。这样测试再启动的子进程不会只因父进程退出就留在后台。停止之后还要等待退出、reader收完管道、writer结束，才把结果交回执行器。

计时主要包住等待退出和收输出，不能把它说成覆盖所有启动、stdin写入阶段的端到端限时。超时会保留 `timed_out` 和退出状态；取消继续向上抛，同时writer保留中断输出。这里保证的是“程序收齐了自己启动的活动”，不是“已经写过的文件自动恢复”。

## 第四步：如果让子Agent帮忙，为什么还要更严格

假如这次任务较大，主Agent把一部分工作交给另一个能写代码的子Agent。只把它的cwd改成独立工作树还不够：shell仍能写绝对路径。工具层的 `WorkerBoundaryGate` 因而先检查只读限制、父会话已有的拒绝条件，以及是否真的能启用OS隔离。

真正启动时还有 `RequiredSandbox.launch` 再查一次。系统没有可用且已启用的隔离，就拒绝worker的命令和通过 Bash 执行的 Skill 脚本，不退化为裸执行。Windows Job能帮助结束进程树，却不能据此宣称提供了同等的文件读写隔离。

子Agent有时需要执行放在用户目录里的Skill脚本。普通规则会保护用户私有目录，不能为了让它能读脚本就开放整个HOME。因此 `PythonSkillTool` 先确认资源目录与摘要，再通过注入的 `skill_read_grant` 只允许读这个Skill根。`RequiredSandbox.for_skill`继续保留原来的工作区写限制和网络设置。

## 为什么框架没有替我们做掉这些事

对Deep Agents来说，Bash只是一个带输入参数说明（schema）和异步执行函数的工具。框架负责把模型调用送进这个函数，工具执行器负责审批；框架不会自动知道应该用哪个Bash、哪些环境变量是秘密、如何杀掉孙进程。

这些机器相关动作留在Sandbox模块。`SandboxModule.bash`构造当前设置下的Bash，`backend/worker`选择隔离实现，`process_runner`交给Bash、Skills和Hooks共同使用。输出writer由工具模块提供，所以机器执行和结果保存能够接起来，但没有相互复制实现。

构造模块时没有运行测试。`composition.runtime`登记好这些函数，等框架真正调Bash才执行。替换沙箱实现也必须报告真实状态，不能对外返回enabled却在内部直接裸跑。

| 读到这一步想回查什么 | 函数 | 交回的内容 |
|---|---|---|
| 当前机器隔离可用吗 | `status/usable` | available、enabled、原因 |
| 实际启动参数是什么 | `Bash.execute`、`launch` | 受限制的argv和过滤后的环境 |
| 大输出和超时怎样处理 | `run_process` | writer结果、退出码、超时状态 |
| 谁结束整个进程树 | `stop_process` | 等待退出后才返回 |
| 子Agent能否退化执行 | `RequiredSandbox.launch` | 满足限制才启动，否则明确错误 |

## 回到这次测试，出错时该怎么理解

**找到sandbox-exec就足够了吗？** 不够。`usable`真的启动短进程，系统禁止执行时仍是不可用；status返回状态，不把普通诊断说成命令已经执行。

**用户批准以后沙箱失效呢？** 启动前重新检查并拒绝。批准的是有这些限制的一次调用，限制改变就不能继续用旧批准。

**测试卡住，取消是不是只关界面？** 不是。上层取消工具任务，runner结束进程组并收reader；这些清理完成前不会假装活动已消失。

**日志一半是中文，字节块刚好切开呢？** 实时显示使用增量decoder；完整输出仍存原始字节，tail预览也处理UTF-8边界。

**命令退出码非零一定有统一错误码吗？** 退出码与is_error是主要事实；普通command非零不一定附额外error_code，超时和Skill/Hook前缀有自己的明确分类。不能只读一个字段。

**on-auto能省掉所有审批吗？** 不能。它还要通过命令白名单和沙箱状态检查；未知命令、危险组合及其它外部效果不因此获准。

读到这里，不妨先问自己：cwd为什么不是隔离，为什么连创建进程都要等到拿到对象再取消，为什么超时后还得继续收管道？把这三个窗口讲清楚，比说“用了asyncio和沙箱”更能说明实现。
