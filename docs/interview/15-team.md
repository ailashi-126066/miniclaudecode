# 团队：把 parser 的测试分出去，怎样收回结果

上一章确认了修复范围。现在主助手准备改 parser.py，用户允许把测试工作分给另一个助手。并行带来的问题不只是多发一次模型请求：测试助手改的是哪份代码，等审批时谁来回答，完成通知有没有真正送到，最后谁能把修改合回主目录？

```text
主助手登记“检查并补充parser测试” → 派发worker
→ 子助手在独立worktree读取已有代码、补测试 → 请求自己的命令审批
→ 把发现发送给主助手 → 主助手等待并收到已保存的结果
→ 审查worker差异 → 用户批准这一次合并 → 核实合入后再清理
```

例子假定双方从同一个已提交基线出发：主助手修实现，子助手先针对基线中的缺陷补测试。子工作区默认不含主目录的未提交修改，不能声称子助手已经验证了尚未共享的新实现；最终合入后仍要独立跑整体测试。

## 第一步：登记工作，再创建独立子会话

主助手先通过任务工具登记测试任务，说明输入、预期结果与依赖。`TeamManager.create_task` 检查任务数量和依赖是否有效，再把新任务交给团队日志保存。任务板解决的是“谁要做什么”，不是创建执行线程；创建和认领任务因此是独立入口。

`spawn_agent` 经 `TeamTool.execute` 进入协调器时，调用者身份来自组装好的当前成员，模型不能在参数里自称别人。`AgentTeam.spawn` 在锁下检查模式、并发名额和依赖，先把成员写为 starting，并在需要时同一次保存任务认领。只有日志成功，才启动创建工作区的异步任务；审批等待中的子助手也占并发名额。

worker 使用独立 Git worktree，readonly 助手则保持只读。`ConfiguredChildSessions.open` 用所选模块在子目录打开普通 `AgentSession`，保留父会话的凭据来源，同时禁止嵌套委派、关闭子长期记忆和 MCP。子助手不是一段在主会话里同步跑完的提示词，而是有自己历史、模型调用与关闭过程的会话。

启动成功后，`AgentTeam.drive` 才运行子会话；`spawn` 返回不代表测试已经做完。子运行遇到审批，drive 保存对应问题并通知主界面；完成时则把成员终态、任务状态和发给主助手的完成通知放进同一条 `team_transition`。这种保存方式避免界面看到成员完成，却永远找不到完成通知。

## 第二步：追加“也测空输入”，消息什么时候算送到

主助手发现还需要空输入用例，调用 send 给测试助手。`TeamInbox.send` 检查收件人和消息额度，先把正文写入团队日志，再发刷新事件。返回成功只表示团队接收了这条消息，不表示子模型已经读到；UI 的“新消息”提醒更不能替代真实接收记录。

正在运行的子助手，下次进入框架的 `HistoryMiddleware.abefore_model` 时，才通过当前成员的 `flush_inbox` 检查自己的收件箱。消息先从 pending 改成 delivering，意思是“这次交付正在处理”；随后提交到该运行的持久输入队列。确认 `input_queued` 已写成，才能把团队消息改为 delivered，这一步在代码里叫 ACK，也就是确认送达。

如果接收方恰好结束，这次输入会被拒绝，消息必须退回 pending，不能因为预约过就打上已送达。空闲且允许继续的子助手可以因新显式消息重新启动一轮，但要等待空名额，并按首次新消息的顺序调度。重启进程不会替旧 pending 消息自动运行任务，取消中也不能重新唤醒。

## 第三步：主助手等待结果，先保存工具结果再确认消息

主助手修改实现后调用 `wait_agents`，希望拿到子助手的测试发现。这里收到消息的方式与上一步不同：`TeamInbox.wait` 把消息预约给这次工具操作，将消息 ID 放进返回结果，但不立即改成 delivered。因为结果刚在内存里生成时，进程仍可能被取消，主助手的历史里还没有任何可重读的通知。

结果交回统一工具结算过程后，`ToolSettlementMiddleware.settle_ready` 先调用注入的 publisher。publisher 使用正常消息保存函数，把正式 ToolResult 写入主会话日志，再绑定完整输出和相关文件事实。此后 `TeamMember.settle_tool` 才从成功结果中取出确切消息 ID，确认这些消息；最后才发布工具完成事件。

因此 ACK 的依据是“主会话有可核实的成功接收记录”，不是“wait 被调用过”，也不是“UI 好像显示过”。工具被中断、保存失败或返回错误时，未确认的预约释放回 pending，下次可以重新接收而不丢消息。下方的框架结算节点通过 publisher 接到消息保存，并非 TeamInbox 自己调用界面来制造成功。

## 第四步：测试文件写完，也不能直接合并和删除工作区

测试助手报 completed，只表示自己的运行结束。主助手先调用 `review_agent` 查看改动，包括新增的测试文件；`WorktreeManager` 用单独的临时 Git index 生成候选文件树，不改 worker 本来的暂存区。显示的 diff 可以截断，但检查内容是否变化的值必须包含完整候选，不能只比较一个统计表。

接着 `merge_agent` 到达更外层的 `TeamToolGate`。它检查任务依赖、worker 是否已停止以及此前是否审查过，再取得绑定源文件树、源提交和目标分支/提交的预览，为**这一次操作**强制请求用户批准。即使前面选择了 Plan auto，这里也不能跳过；批准期间任何一边变化，旧预览都作废。

真正执行 Git 前后，服务再次核对源、目标和结果。发生冲突时保留 worker 与恢复记录；准备解冲突本身需要独立批准，子助手只在自己的文件范围内处理，再重新审查并批准合并。Git 操作已经开始后遇到取消，要等它真实结束、记录到底发生了什么，再向外传播取消。

只有确认目标包含这次合入提交、工作树状态允许清理后，才删除对应 worktree 和分支。Git 检查不等于 pytest 通过，主目录合并后的整体测试还要另外执行并保存结果。清理失败则保留原因和材料，不能把“成员任务完成”直接翻译为“代码已验证并删除”。

## 第五步：用户取消或进程重启，哪些事情还会继续

用户取消测试助手时，`AgentTeam.cancel` 先撤下它再次被消息唤醒的资格，再取消并等待启动或运行任务退出，然后保存终态。创建工作区可能已经进入线程操作，所以取消不能只丢掉协程引用；迟到创建的资源仍要关联到成员记录，之后才有办法检查和清理。

重新打开团队时，`initialize` 读取每条保存的 transition，整条校验后恢复成员、任务和消息。旧 running、starting、needs_approval、merging 不自动续跑，而转成 interrupted。对 delivering 消息，恢复过程核对真实收件会话的日志，或者成功 wait 结果里的消息 ID；找不到确认依据就不能冒称已送达。

最终关闭会话时，团队会等待所有仍登记的任务，并关闭子会话和账本。存储出错时团队停止继续调度，而不是靠未经确认的内存状态接着干。下一章回到用户看到的终端：这些运行、消息和审批如何被显示，为什么主助手等待时仍能回答子助手的问题。

## 框架在刚才的故事里做了什么

Team 并发由 `asyncio.create_task` 管理，协调器登记任务并读取完成异常；没有远程 HTTP Agent 服务，也没有安装另一套 `AsyncSubAgentMiddleware`。每个子会话使用普通 `AgentRuntime` 和 Deep Agents 图，所以模型与工具循环、等待问题和恢复仍复用同一实现。

Team 工具经过普通 ToolExecutor 和 ToolSettlementMiddleware；worker 命令经严格沙箱和强制审批，合并经 TeamToolGate。fork Skill 与 Hook 的只读委派也经 `TeamModule.delegate` 创建的同一协调器路径，以框架 AIMessage 适配结果，不保留旧同步子助手执行栈。账本先保存、模型接收后再确认等可靠性规则，是项目在框架调用边界上补的业务处理。

下面的表格供查找使用。lead 就是主助手，worker 是有独立工作区的子助手；transition 是一条同时保存关联变化的日志，ACK 就是有真实接收依据后的送达确认。角色文字本身不会扩大任何权限。

| 想查什么 | 到哪里找 | 不能仅凭它断言什么 |

## 查找：保存的状态怎样解释

| 字段或记录 | 可以出现的值或内容 | 读到它时要注意什么 |
|---|---|---|
| 成员活动状态 | `starting/running/needs_approval` | 包括等审批在内，都计入并发上限 |
| 成员结束状态 | `completed/failed/cancelled/interrupted` | 不代表已合并；新显式消息可让允许继续的成员再跑一轮 |
| 合并状态 | `merging/merged`、`merge_commit` | Git结果另行核对，清理也有额外条件 |
| 任务状态 | `open/in_progress/done/failed/cancelled` | `assignee`、`done_by`和依赖限制谁能认领与合入次序 |
| 收件箱状态 | `pending/delivering/delivered/dropped` | 分别为待送、处理中、已送达、已丢弃；`delivery`记录方式和负责本次交付的操作 |
| `team_transition` | 变化的成员、任务、消息和记录ID | 关联变化一次追加，不能只保存了成员却漏掉通知 |
| 主会话的`team_agent` | 子成员、会话、目录、模式、类型和角色 | 用来找到子对话并汇总用量，不把子工具当主会话直接执行 |
| 子会话的`team_parent` | 主会话ID、成员ID、模式与角色 | 找回由谁派发、按什么权限打开 |

## 遇到异常时，程序怎么处理

**角色写“管理员”可以写 lead 工作区吗？**

不能。worker 文件根固定在自己的 worktree，readonly 固定只读；权限不从 role 推导。

**Linux 没有严格沙箱能运行 worker Bash 吗？**

不能回落为无隔离命令。文件工具是否可用与命令是否可执行分别判断，只读助手仍可使用允许的文件读取。

**worktree 是否包含 lead 的未提交修复？**

默认不含，创建参数明确 include_uncommitted=False；因此派发前要说明共享基线。

**wait 被取消，预约消息会丢吗？**

没有正式成功ToolResult就退回待送；重启也核对真实接收记录，不能把合成中断结果当作已收到。

**merge 审批期间代码又变了？**

旧 preview 失效，拒绝合并，要求重新 review 和审批；不能把“之前批准过”当通行证。

**合并已成功但取消紧接着到达？**

merge等待自己已经启动的Git操作真实结束，并保存真实结果，再传播取消，避免留下“取消等于没发生”的错误判断。

**账本保存失败怎么办？**

团队进入 degraded，后续等待／操作明确报存储错误，不继续用未经确认的内存状态调度。


## 面试常见追问

- **为什么不用 HTTP 多 Agent？** 当前目标是本地同进程协作，asyncio 足以管理任务，不需要远端身份与网络协议。
- **为什么需要独立 Team JSONL？** 团队状态变化不能移动 lead 的对话分支叶节点，也不能冒充模型消息。
- **为什么 reserve 不直接 delivered？** 预约后可能取消、保存失败或 run 已结束，只有目标日志中有真实接收依据才标已送达。
- **为什么 task done 不能直接清理 worker？** 完成任务与目标是否包含子改动是两回事，还要读差异、批准这次合并、核对Git结果及工作区是否干净。
- **FIFO靠什么？** wake_eligible 的首次新消息顺序，加可用名额和显式状态判断，不按agent创建顺序猜。
- **自动计划为什么不能免 merge 审批？** 合并改变主工作区，外层强制检查固定了这次要合入的源内容与目标提交。

子助手自己的模型、工具和日志在后台运行，用户仍要看清是谁等待批准。接着读[终端界面](16-ui.md)，沿着屏幕上的输入、审批、结果卡片和退出，核对这些动作如何回到真实会话。
