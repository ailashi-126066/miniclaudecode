# 界面：用户怎样看到审批、测试输出和取消结果

上一章的主助手和测试助手可以同时工作，但用户不该靠猜测判断谁在等批准。本章仍沿用“修复 parser.py，并跑测试”：从敲下请求，到看到测试命令、同意一次、展开完整输出，最后退出终端，逐步说明 Textual 和应用服务如何合作。

```text
打开TUI → 通过统一应用入口打开会话 → 输入修复请求
→ 一项主操作在后台运行，模型事件送到Textual消息泵
→ 显示对应主/子会话的审批 → 用户答案回到原运行
→ 正式结果保存后刷新历史 → 点击输出只读已有对象
→ 取消/退出先等待任务结束，再关闭会话
```

界面是用户操作入口，也是一名事件接收者。它不重新实现模型循环，不把“按钮点了批准”当成工具已经成功执行。

## 第一步：窗口打开之后，才打开用户选中的会话

CLI 从统一 `Application.tui` 取得界面对象。应用组装把配置、所选模块和会话打开能力交给 `UIModule.tui`，后者创建 `PyApp`。此时只是创建 Textual App，还没有因为画窗口就请求模型或创建一套独立数据库；界面拿到的是 `InteractiveSessions`，也就是打开和列出会话的接口。

Textual 挂载页面后才调用 `PyApp.on_mount`。它连接输入补全组件、读取沙箱状态，并通过 `switch_session` 打开初始会话。`ConfiguredInteractiveSessions.open` 解析会话名称或 ID，将 PyApp 作为事件消费者交给正常应用会话入口。前面章节的恢复、Plan 初始化、模型资源和关闭过程都因此被复用。

切换会话先停止当前操作，目标打开成功后再关闭旧会话并替换页面状态。旧关闭失败时，新打开的对象也必须关闭，不能让一个窗口偷偷留下两条运行。成功后清掉旧流式文字和工具控件，再从新会话读取历史；后续迟到事件也要检查会话 ID，避免把旧测试输出画到新页面。

## 第二步：敲下请求，只开一项主操作；补充输入另走队列

`PyApp.send_text` 先判断输入是哪一种。以 `/` 开头的命令交静态命令表解析；空闲时的普通文字生成用户消息，交 `active_session.run`；正在运行时的普通文字则按 steer 或 follow_up 调 `submit_input`。界面不能因为用户又按一次回车，就并行覆盖原来的主任务。

真正执行由 `start_operation` 创建的 asyncio task 承担，引用放在 `_operation` 中供 busy 判断、取消和等待。`execute_operation` 调用传入的应用函数；若返回 `RunResult`，再经会话统一发布结果并刷新状态。这里没有使用 Textual Worker 装饰器，更没有由框架自动保存一条“后台工作队列”。

用户补充“只跑 parser 测试”时，Queued 只说明会话已把 `input_queued` 写入日志，不是模型已经照做。团队有消息要求主助手继续时，`maybe_wake_team` 也先等 UI 空闲、没有待答主运行，再走同一个主操作入口。排他规则因此同时约束用户输入和团队唤醒，不靠哪个按钮最后改了 busy 标志。

## 第三步：屏幕能实时变化，但正式历史有另外的来源

模型一边思考一边返回文字，工具也会发布开始和完成事件。`EventStream.emit` 按序把事件交给消费者，但 `PyApp.consume` 不在这个后台调用里直接修改控件。它只用 `post_message` 投递 Textual 的 `RuntimeEvent`，稍后消息泵调用 `on_py_app_runtime_event` 才真正渲染。后台摘要任务也能发事件，这个间接步骤避免它在不合适的任务上下文里操作页面。

`render_runtime_event` 先核对会话身份，再按类型处理。文字 delta 只更新临时区域；正式消息结束事件则清理临时文字并调用 `render_history`。后者从 `session.inspect(presentation=True)` 读取已经保存的历史，按消息 ID 复用已有控件。这解释了为什么断流前屏幕上出现的半句话，不能自动拼成下次打开时的一条成功回答。

历史、模型实际上下文和用量估算也分别返回。摘要可以让模型少读旧消息，但界面仍能展示原始对话；token 数据缺失时标为不可用，而不是猜精确数字。如果显示异常，界面停止继续渲染并提示，不会重跑工具来“补画面”。事件漏了可以重新读取历史，磁盘日志才承担已完成结果的恢复。

## 第四步：批准只回答一个问题，展开输出只读一份结果

测试命令需要确认时，`ApprovalPanel` 显示当前操作的内容，用户选择 Approve once 或 Deny。控件发送带 `operation_id` 的 Responded 消息，主 App 再把答案交给 `resume`。它不直接执行 Bash，也不保存一个永久允许开关；运行时仍会核问题是否有效、审批内容是否改变。Plan、普通提问和 MCP 请求使用各自答案面板，不能都套成 approve/deny。

子助手审批还带 `agent_id`。主助手可能正在 `wait_agents`，若把所有答案都塞进主 `_operation`，用户会被 busy 挡住。因此 `on_approval_panel_responded` 为子答案创建独立的 `answer_child` task，交团队恢复指定子会话；关闭时仍把这些 task 一并取消和等待。独立答复不代表子助手获得绕过审批的另一条执行通道。

工具完成以后，卡片可通过 `output_id` 展开完整测试输出。`read_next` 把行位置和字节位置交给会话只读接口，更新下一页游标；它读的是已经保存的对象，从不再次运行 pytest。读取也必须经过当前会话的输出存储校验，不能从界面参数直接拼磁盘路径。

用户最终退出时，`shutdown` 先阻止新渲染，停止并等待主操作，再取消和等待子审批任务，最后关闭会话。前面章节的模型连接、Hook、记忆和团队因此沿同一关闭路径结束。到这里，“修复请求已经保存”“测试批准已回答”“工具结果可重读”和“窗口已关闭”才各有明确依据；后面的评测章节会说明如何从这些记录之外独立判断修复是否正确。

## 框架在刚才的故事里做了什么

`PyApp` 继承 Textual `App`，`compose` 声明组件，`on_mount` 处理挂载，`Binding` 将键盘动作送到面板方法。`RuntimeEvent` 与面板的 Responded 都是 Textual Message，由框架消息泵分派；`UsageScreen` 是 ModalScreen，关闭它只退出用量窗口，不取消模型。

框架没有替项目决定会话运行规则。应用端口连接真实 `AgentSession`，项目显式维护主 asyncio task 和子答复 task，负责排他执行、取消等待、会话身份过滤、完整输出分页和渲染失败处理。CLI 的 ConsoleOutput 是另一个消费者，与 TUI 共用应用服务，但不会把 Textual 控件当作持久化后端。

下面用表格补充字段索引，供读完故事后查询。图和节点里的“回调”表示框架稍后调用，不表示 `consume` 同步调用渲染函数；“消费者”只表示接收事件的一方，不代表它拥有业务结果。

| 展开的测试输出 | `output_id`指向的完整结果对象 | 对象仍保留且归属检查通过才可读取，不重新跑测试 |
| 输入命令补全 | `CommandRegistry`和当前分支技能目录 | 只是输入帮助，查到名称不等于已批准执行 |

漏掉一次界面刷新不等于丢了结果，可以重新读取已保存历史。反过来，流式画面曾显示的内容也不能代替完整消息。

## 遇到异常时，程序怎么处理

**打开时还没拿到 state 就点按钮？**

active_session／view_state 抛 session_unavailable，而不是在 None 上继续执行。

**lead 正在 wait，child 的批准会卡在 busy 吗？**

不会走主 start_operation；带 agent_id 的答复另建独立答复任务并刷新状态。

**关闭后还能点旧批准吗？**

旧控件不能替新进程回答已经消失的等待；重新打开会话会整理保存的记录，并让旧等待过期。

**流式文字中途断了，历史是什么？**

只有完成消息正式保存后才进入原始历史；partial留在当次显示，不拼接成下次成功回复。

**一个控件渲染抛异常会怎样？**

_render_failed阻止后续渲染并提示重新打开；不会把异常当作模型或工具成功。

**展开输出会重新跑命令吗？**

不会。读的是output_id对应对象，next_offset／next_byte_offset推进读取位置。

**退出时还有任务没结束？**

shutdown先标_closed，stop_active并等待主操作，再取消并等待所有子审批任务结束，最后关闭会话。


## 面试常见追问

- **为什么不在consume里直接改控件？** 模型和摘要任务不是Textual消息泵，统一投递避免跨上下文改UI。
- **为什么既有事件又有inspect？** 事件负责及时显示，inspect负责重新读取已保存记录，它们承担的事情不同。
- **为什么子审批有独立任务？** lead可能仍在运行，不能拿lead的主操作任务当作所有子助手答复都必须等待的入口。
- **面板Approve once等于永久授权吗？** 不等于；答案绑定operation_id，执行端仍校验当前问题和具体内容。
- **为什么历史列表要entry_id缓存？** 完成记录不可变，增量复用避免每个token重建整段历史。
- **怎么区分应用完成和显示完成？** RunResult及JSONL记录实际运行结果；控件成功更新只是展示动作。

用户已经看到测试输出，但界面上的“完成”还不能独立证明修复正确。接着读[评测](17-evaluation.md)，看怎样在隔离任务里重新运行测试，并保存能逐项核对的证据。
