# Java 源码解析：当前上下文管理、压缩与恢复

本文按调用顺序说明代码做什么：`Agent` 每轮请求模型前先处理工具结果；Token 接近窗口上限时，再压缩较早消息并保留最近消息。

相关代码主要在下面几个文件中：

- `src/main/java/com/mewcode/agent/Agent.java`：主循环，决定何时执行预算与压缩。
- `src/main/java/com/mewcode/toolresult/ToolResultBudget.java`：第一层，工具结果落盘和替换。
- `src/main/java/com/mewcode/compact/ContextCompactor.java`：第二层，判断是否压缩、请求摘要、重建对话与恢复块。
- `src/main/java/com/mewcode/compact/RecoveryState.java`：保存压缩后仍要继续使用的文件路径、Plan、验证结果和审批决定。
- `src/main/java/com/mewcode/agent/StreamingExecutor.java`：在 `ReadFile` 成功后记录文件路径，并记录测试、构建、检查命令的结果。

---

## 1. 先看一轮 Agent 的主线

入口是 `Agent.run(...)` 的循环。每一轮都会先执行工具结果预算，再判断是否需要压缩会话。

```text
Agent.run 的单轮循环
  ↓
计算本轮可用工具表 iterToolSchemas
  ↓
ToolResultBudget.apply(...)        ← 第一层：控制工具结果
  ↓
ContextCompactor.manage(...)       ← 第二层：必要时压缩早期会话
  ↓
client.stream(..., iterToolSchemas)
  ↓
StreamingExecutor 执行工具；ReadFile 成功时记录恢复路径
  ↓
进入下一轮
```

`Agent` 在调用压缩前就计算 `iterToolSchemas`，并把同一份列表同时传给 `ContextCompactor.manage(...)` 和后面的 `client.stream(...)`。这样压缩后恢复块里列出的工具，与下一次真正提交给模型的工具是一致的。

核心调用位于 `Agent.java`：

```java
List<ContentReplacementRecord> newRecords =
        ToolResultBudget.apply(conv, sessionDir, replacementState);

String compactMsg = ContextCompactor.manage(
        conv, client, contextWindow, maxOutput, wd, sessionId,
        compactTracking, recoveryState, iterToolSchemas,
        usageAnchor, conv.getMessages());
```

`conv` 是当前会话对象。`ToolResultBudget` 会原地替换过大工具结果；`ContextCompactor` 会在需要时原地重建消息列表。后面的 `client.stream` 使用处理后的 `conv`。

---

## 2. 第一层：先控制工具结果，而不是立刻总结对话

第一层的实际实现是 `ToolResultBudget.apply(...)`，不是 `ContextCompactor.offloadAndSnip(...)`。

这个方法遍历 `conv` 中的 `ToolResultBlock`，把超大结果写入磁盘，并把消息中的原文替换为预览文本。

当前阈值在 `ToolResultBudget` 中：

```java
public static final int SINGLE_RESULT_LIMIT = 50_000;
public static final int MESSAGE_AGGREGATE_LIMIT = 200_000;
```

单条 `ToolResultBlock` 超过 50,000 字符时会优先落盘。若每一条都不大、但同一条消息内多个工具结果的总和超过 200,000 字符，则会按结果大小从大到小继续落盘，直到总量回到阈值以内。

落盘文件位于 Agent 传入的 `sessionDir/tool_results/`。替换后的 `<persisted-output>` 包含保存路径和前 2,000 个字符；模型需要完整内容时可调用 `ReadFile`。

`ContentReplacementState` 只在 Java 内存中保存已处理的 tool use id 和替换文本。下一轮再次执行 `apply(...)` 时，它据此跳过已处理结果，不会重复落盘。

`Agent` 拿到本轮新增替换记录后，还会调用 `ReplacementRecordsIO.append(...)` 持久化它们。也就是说，第一层不仅修改内存中的会话，也为后续会话恢复保留替换历史。

### 未接入主链的遗留方法

`ContextCompactor` 内仍有 `offloadAndSnip(...)`，但当前主链没有调用它。它使用的是另一组旧阈值与旧的占位文本，不能代表现在的第一层行为。

因此，阅读当前代码时应把职责理解为：`ToolResultBudget` 管工具结果的落盘预算，`ContextCompactor` 管整个会话的摘要压缩。

---

## 3. 第二层：绝对 Token 触发线

`ContextCompactor.manage(...)` 接收第一层处理后的会话，计算当前 Token，再决定返回、自动压缩或强制压缩。

旧的 `AUTOCOMPACT_THRESHOLD = 0.80` 仍在类中，但注释已经说明它仅为遗留常量；当前判断使用的是“有效窗口减安全边距”的绝对值。

```java
effectiveWindow = contextWindow - min(maxOutput, 20_000)
softTrigger    = effectiveWindow - 13_000
hardTrigger    = effectiveWindow - 3_000
```

`maxOutput` 或 20,000 Token 被预留给模型输出。软触发线调用自动压缩；硬触发线调用 `forceCompact(...)`。

`manage(...)` 的决策主线可以写成：

```text
当前 Token < 软触发线
  → 不压缩，直接继续

软触发线 ≤ 当前 Token < 硬触发线
  → 熔断器未打开时，尝试自动压缩

当前 Token ≥ 硬触发线
  → 强制压缩
```

自动压缩失败会写入 `AutoCompactTrackingState`。连续失败 3 次后，软触发区不再继续尝试，避免每一轮都发送一次必然失败的摘要请求。一次成功压缩会重置失败计数。硬触发仍会走强制压缩，因为这时继续请求模型更容易直接超出上下文窗口。

### Token 是怎样估算的

冷启动时，`estimateTokens(...)` 用 `字符数 / 3.5` 估算消息正文、工具参数、工具结果和 thinking block。

模型返回 usage 后，`Agent` 保存 `UsageAnchor`。`currentTokens(...)` 使用“真实基线 Token + 锚点后新增消息的估算值”，而不是每轮重新估算完整历史。

## 4. 真正压缩时：摘要旧消息，保留最近原文

`autoCompact(...)` 只摘要较早消息，不会删除全部历史。

`computeKeepStartIndex(...)` 从会话末尾选择保留区：约 10,000 Token、至少 5 条消息、最多 40,000 Token。边界落在 tool result 消息时，会把对应的 assistant tool use 消息一起保留。

于是会话被拆成两部分：

```text
较早前缀 toSummarize  → 发送给摘要模型
最近尾部 toKeep       → 原样保留在新会话中
```

代码中的拆分就是下面三步：

```java
int keepStartIndex = computeKeepStartIndex(messages);
List<Message> toSummarize = messages.subList(0, keepStartIndex);
List<Message> toKeep = messages.subList(keepStartIndex, messages.size());
```

`keepStartIndex <= 0` 表示全部消息都在保留区；`keepStartIndex < MIN_KEEP_MESSAGES` 表示旧前缀太短。这两种情况 `autoCompact(...)` 直接返回，不创建摘要请求。

### 摘要请求由谁发出

`autoCompact(...)` 调用 `requestSummaryWithPTLRetry(client, toSummarize, toolSchemas)`。这个方法先调用 `serializeForSummary(...)`，把旧前缀转换为摘要输入：普通消息保留角色和正文；工具调用只保留工具名与 id；每个工具结果最多保留 500 个字符。

`requestSummary(...)` 创建临时 `ConversationManager`，把“摘要系统提示词 + 序列化旧前缀”作为 user message，然后调用：

```java
BlockingQueue<StreamEvent> events = client.stream(summaryConv, toolSchemas);
```

它读取 `TextDelta` 拼接摘要文本，遇到 `StreamEnd` 结束，遇到 `Error` 抛出异常。摘要请求使用当前 `toolSchemas`，但代码没有执行工具调用；这里只收集文本输出。

遇到 “prompt too long” 类错误时，`requestSummaryWithPTLRetry(...)` 先按 API 轮次把最老消息组从 `toSummarize` 移除，再重新请求摘要，最多重试 3 次。

模型输出中的 `<summary>...</summary>` 会被提取出来。若模型没有遵循标签格式，则直接使用原始输出，保证压缩流程不会仅因格式不规范而失败。

### 新会话如何重建

摘要完成后，`autoCompact(...)` 先构造 `content`：早期会话摘要、近期消息已保留的提示、可选的 session JSONL 路径，以及后面生成的恢复块。然后创建新的 `ConversationManager`，把 `content` 作为第一条 user message，再逐条追加 `toKeep`。

```text
新 ConversationManager
  ├─ user：早期会话摘要 + 恢复块
  ├─ 最近的 assistant / tool_use 消息
  ├─ 最近的 user / tool_result 消息
  └─ ...
```

追加近期消息时，`appendMessage(...)` 根据消息类型恢复 assistant tool use、user tool result、普通 user 和普通 assistant 消息。`replaceConversation(...)` 清空旧 `ConversationManager` 内部列表，再把新消息列表写回；`Agent` 和 TUI 继续使用同一个 `conv` 引用。

若当前有 `workDir` 和 `sessionId`，压缩会调用 `SessionManager.saveCompactBoundary(...)` 写入一条 `compact_boundary`。该记录保存摘要、恢复块和 `toKeep` 的角色、文本内容。因此恢复会话时不仅能重建摘要和最近消息，也能重新看到压缩时保存的 Plan、验证结果和审批决定。

## 5. RecoveryState：压缩后还要继续用的运行状态

`Agent` 创建一个 `RecoveryState` 实例，并在调用 `ContextCompactor.manage(...)` 或 `forceCompact(...)` 时传入它。`RecoveryState` 不属于 `ConversationManager`，不会自动作为对话消息发送给模型。

`RecoveryState` 不是模型上下文，它只是 Java 内存里的暂存区。真正压缩时，`buildRecoveryAttachment(...)` 才把其中的内容渲染成一段文本，追加到摘要消息里，模型在下一次请求中才会看到。

它保存五类信息：`files` 记录最近读取的文件路径；`skills` 记录已激活的 Skill；`plan` 保存压缩瞬间的当前 Plan；`validations` 保存最近的测试、构建、lint、check 等命令及其成功/失败输出；`approvals` 保存用户对工具权限的 pending、ALLOW、ALLOW_ALWAYS 或 DENY 决定。同一路径再次读取会覆盖旧时间；验证最多保留 5 条，审批最多保留 10 条。

文件路径由下面这条调用链写入：

```text
模型请求 ReadFile
  ↓
StreamingExecutor.executeSingle(...)
  ↓
recordReadPathForRecovery(call, result)
  ↓
RecoveryState.recordFileRead(path)
```

`StreamingExecutor.executeSingle(...)` 只有在工具名为 `ReadFile` 时才调用 `recordReadPathForRecovery(...)`。该方法会过滤 `recoveryState` 为空、工具执行失败和无效 `file_path` 的情况。

满足条件时，它直接调用 `RecoveryState.recordFileRead(path)`。这里不会再次读取磁盘，也不会在内存中保存文件正文。

同一个 `executeSingle(...)` 还会调用 `recordValidationForRecovery(...)`。它只观察 `Bash` 和 `PowerShell`：命令中出现 `test`、`mvn`、`gradle`、`lint`、`compile`、`build`、`check` 等验证关键词时，才记录命令、成功状态和最多 2,000 个字符的输出。普通 shell 命令不会进入验证记录。

Plan 不由工具执行器保存。`autoCompact(...)` 在构建恢复块前读取 `.mewcode/plans/active.md`，并调用 `RecoveryState.recordPlan(...)`。审批则由 TUI 收到 `PermissionRequestEvent` 时写入 pending，用户在权限弹窗中选择后再写入最终决定。

`executeAll(...)` 会并行执行可并发的读取工具，所以 `RecoveryState` 用 `synchronized (lock)` 保护内部 map。

压缩发生时，`autoCompact(...)` 调用：

```java
String attachment = buildRecoveryAttachment(recovery, toolSchemas);
if (!attachment.isEmpty()) {
    content += "\n\n---\n\n" + attachment;
}
```

`buildRecoveryAttachment(...)` 先写当前 Plan、最近验证结果和审批决定，再调用 `state.snapshotFiles(RECOVERY_FILE_LIMIT)`，按读取时间从新到旧取最多 5 个路径。随后遍历 `toolSchemas`，取每个 schema 的 `name` 和 `description` 第一行。它返回的字符串包含：

- 最近 5 个读取过的文件路径和时间；
- 当前 Plan 的路径和内容；
- 最近测试/构建/检查的命令、成功状态和输出；
- 最近的工具权限决定；
- 当前 `toolSchemas` 中的工具名和描述首行；
- 一条要求模型重新读取精确内容的提示。

这段字符串会随压缩后的摘要一起写入新的 `ConversationManager`。下一次 `client.stream(...)` 时，模型直接看到文件路径和工具列表；模型不需要、也不能直接读取 `RecoveryState`。

模型需要文件内容时，使用路径再次调用 `ReadFile`。新的 `ReadFile` 成功后会更新 `RecoveryState.files` 中该路径的读取时间。

### Skill 恢复目前只是预留能力

`RecoveryState` 还定义了 `recordSkillInvocation(...)` 和 “Active skills” 输出，但当前 TUI 的 `SkillActivator` 没有调用该方法。因此当前恢复块会包含文件和工具，通常不会包含 Skill。

---

## 6. 手动压缩与自动压缩的关系

TUI 的 `/compact` 直接调用 `ContextCompactor.forceCompact(...)`，不检查阈值。它传入当前会话、模型、上下文窗口、会话 id、`RecoveryState` 与工具 schema。

自动压缩由 `Agent` 调用 `manage(...)` 决定；手动压缩由 TUI 调用 `forceCompact(...)` 直接执行。两者最终都进入 `autoCompact(...)`。

---

## 7. 最后用一句话串起来

`ToolResultBudget` 处理工具结果；`ContextCompactor` 处理会话压缩；`RecoveryState` 提供压缩后的文件、Plan、验证和审批状态；`Agent` 在每次 `client.stream(...)` 前调用它们。

阅读源码时，沿着下面这条链即可：

```text
Agent.run
  → ToolResultBudget.apply
  → ContextCompactor.manage / forceCompact
  → autoCompact
  → buildRecoveryAttachment
  → client.stream
  → StreamingExecutor.recordReadPathForRecovery
```
