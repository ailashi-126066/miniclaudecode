# 第二个计划（唯一实施计划）

更新时间：2026年10月13日（Asia/Shanghai）。

## 目标和实施边界

本次实施以第二个计划.md（本文件）和用户最新要求为准。第一计划已逐条核对；确认实现的要求作为冻结行为基线，未实现、未验证和无法确认的要求已经迁入本文件。第一计划文件在迁移核对完成后删除，不再维护第二份实施规范。

在保留 pycode 原有功能的基础上，复用 Deep Agents、LangChain、LangGraph 的现有组件，减少重复实现。每项职责只有一个主要实现，不同时维护两套历史、长期记忆注入或自动压缩流程。

本次计划处理提示构造与结构化输出、记忆与上下文管理、Agent 图内的 LCEL 编排、主模型工具筛选／故障切换／统一工具错误反馈，以及仅限命令注册、前缀匹配、候选弹窗的命令补全。主 Agent 的业务 system prompt 继续由项目管理；完整历史保存、历史投影、工具结果驱逐、回读、80% 提前后台摘要与安全采用机制保持现有行为。长期记忆按用户要求改为 JSON 唯一内容存储，接入官方 Store Manager、主动记忆和搜索工具；默认自动提取、自动写入，无需人工审批。

LCEL 部分属于等价重构：保持现有步骤、依赖顺序、允许并发的范围、锁、异常处理、取消收拢与结果结算。工具筛选、模型故障切换、工具错误反馈，以及 JSON 存储迁移、主动记忆／搜索工具、取消记忆审批和完善提取恢复属于用户另行要求的功能调整，单独实施和验收，不宣称这部分仅是换写法。

80% 提前后台压缩是核心默认功能，不作为可选扩展交付，不要求用户额外开启。输出预留和安全余量导致更早触发时，继续使用现有预算规则。

本文件是实施计划。所有待办项在完成实现和相应验证后才能勾选。

## 框架和项目的职责

### 框架承担的部分

- Deep Agents：保持现有主 Agent 入口，执行模型与工具循环，继续提供文件工具、Skills 和子 Agent 等已接入能力。
- LangChain 消息与模型接口：表示 system、user、assistant、tool 消息，调用配置的模型。
- ChatPromptTemplate：用于记忆提取、历史摘要等内部请求中需要变量填充的提示；不接管主 Agent 的业务 system prompt。
- with_structured_output：模型与服务支持且协议兼容验证通过时，取得符合记忆字段结构的结果；保留原始模型响应用于现有结算与计费。不能仅因接口存在就自动切换请求协议。
- LangMem：create_memory_store_manager 通过同一个 JsonMemoryStore 自动查询、整理与更新语义／情景记忆；create_manage_memory_tool、create_search_memory_tool 提供主 Agent 执行中的主动记忆与搜索；Prompt 包装规则身份、正文和更新要求，单条规则使用 create_prompt_optimizer(kind="prompt_memory")，多条相关规则使用 create_multi_prompt_optimizer。记忆后台启动继续使用现有 asyncio.create_task，不接入 ReflectionExecutor。内部模型调用接入受控适配层，项目负责 JSON 持久化、来源校验、提交恢复和有界上下文投影。不再单独运行旧提取器或重复调用 create_memory_manager。
- RunnableSequence／管道组合：按现有顺序串联图内确定的子步骤，前一步输出交给后一步。
- RunnableLambda：把现有输入整理、受控模型调用、完整性检查和服务入口接入 LCEL，不在包装器内重复实现业务规则。

- RunnableBranch：表达已有条件分支；条件、判断优先级、连续阶段和执行动作均保持原有语义。
- AgentMiddleware：提供模型调用前后的接入点，承载现有历史投影、驱逐和后台摘要调度的调用边界。
- LLMToolSelectorMiddleware：在当前任务允许且已披露的工具中选择本次主模型需要的工具；必需工具按 always_include 保留，选择模型接入受控计费。
- ModelFallbackMiddleware：主模型在既定重试后仍遇到允许切换的 Provider 故障时，按配置顺序尝试兼容备用模型；每次实际调用仍由项目记录模型身份、预算、费用和错误。

- LangGraph：继续提供图执行、消息状态、当前运行 checkpoint、interrupt 和 resume 等已接入能力。

### LLMToolSelectorMiddleware：主模型前筛选工具

```text
刷新当前 MCP／工具声明
→ SkillsMiddleware 按现有规则披露工具
→ 应用 Plan、Skill、只读角色与作用域限制
→ 官方 LLMToolSelectorMiddleware 选择相关工具
→ 合并当前允许范围内的 always_include 必需工具
→ 记录最终 Schema／提示快照并校准预算
→ 主模型请求
```

在现有 create_deep_agent／Middleware 调用链接入官方工具选择器，不另建工具加载或执行循环。MCP 与 Skills 候选来自当前 run 的真实声明，选择器只筛选已披露且允许使用的工具，不加载未选 Skill 正文、执行工具或扩大权限。动态披露后工具集变化时重新按本次请求选择；不在整个会话里永久删除未选工具。

always_include 由项目配置和任务模式确定，保留完成任务必需的读取／发现／回读工具、当前需要的审批／提问／计划出口和记忆工具。必需工具也必须先通过作用域限制，不能因 always_include 恢复 PLAN、只读 Worker 或 Skill 已禁用的工具。max_tools 控制可筛选工具数量，不作为业务调用次数上限；always_include 工具及 Provider 专有工具按所选版本接口单独计量，不能声称所有工具 Schema 都被压到 max_tools。

选择器模型由 ModelFactory 创建并接入受控适配层，选择输入为组件支持的任务消息与候选名称／说明，输出只允许候选工具名；程序检查未知名、重复名和声明版本。候选较少或没有可选项时跳过选择请求。配置选择模型、候选数量／Schema 触发条件、max_tools、always_include 和错误退路，并固定默认值验收；不凭空指定外部备用 Provider。

选择请求失败或结果无效时明确记录，退回筛选前已经通过权限／披露过滤的工具集合，继续做真实预算检查；容量仍不足时交给原有摘要／容量错误路径，不能静默截掉工具或只留下不可完成任务的集合。同一次主模型请求的重试和备用模型尝试复用选择快照，不重复调用选择器。工具 Schema 总量减少的收益需与额外选择请求的费用和耗时一起评估。

现有 HistoryMiddleware 后续追加 registry 工具的步骤需同步调整，不能把选择器刚移除的全部工具加回来。最终 prepare_model_boundary／Skills 边界在筛选之后记录实际工具和提示，确保 ContextMeter、摘要配置哈希、界面容量和真实请求一致。未选工具仍保留在可发现注册表中，执行时继续核对本次声明、权限和版本。

### ModelFallbackMiddleware：重试后按配置切换模型

```text
固定本次消息、工具选择快照和逻辑请求身份
→ 按实际主模型配置校准能力和输入／输出预算
→ 主模型的现有 ModelRetryMiddleware＋逐次计费
→ 成功：保存唯一完成回复
→ 重试后仍有允许切换的 Provider 故障：官方 ModelFallbackMiddleware 尝试下一模型
→ 每个备用模型重新校验能力／预算并独立记录请求与用量
→ 成功继续同一主 Agent；全部失败保留现有错误结算
```

备用模型列表由用户／项目 Provider 配置提供有序引用；ModelFactory 构造已配置的 BaseChatModel 实例并注入官方 ModelFallbackMiddleware，未配置时只运行主模型。组件负责候选切换，项目不再维护第二套 fallback 循环；主图、输入快照、审批和已完成工具事实保持同一份，不因模型切换重启任务或重跑工具。初版仅接管主 Agent 模型请求，不自动扩展到后台摘要、记忆、优化或工具选择模型。

复用现有故障分类，只允许 Provider 连接／超时、可切换的服务故障和重试耗尽的限流等进入切换流程。用户取消、GraphInterrupt／GraphBubbleUp、权限拒绝、配置／参数错误、程序错误、持久化失败和内容拒绝不作为切换理由；context_overflow 先走已有预算和安全摘要路径，不能通过切换绕过处理。官方组件可能捕获通用 Exception，接入适配必须验证错误筛选：不允许切换时不发送下一候选请求，并向外保留原始错误，不能假设组件天然提供 retry_on 参数。

每个候选在一次逻辑请求内使用现有有限重试策略；避免在整个 fallback 外再套一层重试而从主模型重新开始。已有 SDK 自动重试配置与 ModelRequestRunner 保持统一，组件切换和内部重试请求均如实结算。

ModelRequestRunner 的 selection、Provider 观察器、价格／缓存用量映射、事件和最终 Message.model_selection 必须对应实际执行模型，不能把备用请求记在主模型名下。失败候选与成功候选关联同一 logical_id，分别保留 request_id、候选序号、attempt、实际 provider／model_id 与状态；主请求 purpose 不被选择器请求或备用请求覆盖。流式失败候选的 partial 保持其失败身份，界面按请求切换更新，不拼接成成功回答，也不执行残缺工具参数。

切换前检查工具调用、结构化／图片／推理消息支持和上下文窗口，按候选 API 转换消息与专有参数，保留原始 JSONL。不能机械复用主模型的 reasoning、缓存字段或输出额度，也不能默默丢弃必需内容。按候选的实际窗口、输出预留和最终 Schema 重新校准 ContextMeter；候选能力变化使不匹配摘要缓存失效。模型能力不满足时记录跳过／失败原因，不发送明显无效的请求。运行内切换不自动修改用户持久首选模型；只有完整成功回复进入正式历史一次。

### ToolErrorMiddleware：执行异常转成可恢复的正式工具结果

```text
ToolSettlementMiddleware 建立调用／权限／快照边界
→ 工具执行 handler
  → ToolErrorMiddleware 处理允许反馈给模型的异常
    → 既有 ToolRetryMiddleware 仅重试允许的只读临时失败
      → 实际工具执行
→ 成功或 error ToolMessage 转换成同一领域 ToolResult
→ 发布输出／绑定快照／写入唯一 JSONL 结果
→ 发送正式结束事件，交回主模型
```

按公开接口配置 on_error／aon_error 和需要覆盖的工具范围。ToolErrorMiddleware 不调用模型、不自动重试，负责将可处理异常转换为配对 ToolMessage(status="error")，保留原 tool_call_id、工具名和稳定错误码。模型可依据结果修正参数或换方法；已有同名／同参数／同错误连续失败阻断继续生效。

错误转换放在现有执行／结算边界内部，ToolRetryMiddleware 对可重试的只读异常先重试，耗尽后按 on_failure="error" 交给错误转换。写入、Shell、外部副作用、MCP 或其他来源继续遵守原有重试策略，不因为接入错误组件而扩大重试范围。

项目工具已经返回 ToolResult(is_error=True) 或原生 error ToolMessage 的情况直接沿用，不再转换一遍；允许交给模型修正的异常由统一映射转成稳定领域失败，移除对应重复捕获／包装路径，保留正式 error_code、执行／副作用不确定性和必要输出引用。错误内容不原样暴露凭据或无关内部信息。

GraphInterrupt／GraphBubbleUp、取消、JSONL／输出持久化失败、快照结算失败和原有关键同步 Hook 失败继续向上抛出；不能作为普通工具错误让主模型继续。只有输出与 JSONL 正式结算完成后才发结束事件和继续模型循环。动态 MCP、Skill 工具、内置文件工具与自定义工具均需验证异常路径，不允许组件在外围先返回失败结果而跳过快照和 JSONL 结算。

### 接入边界与验收

三项组件属于用户明确要求的功能调整，与 LCEL 等价重构分开验证。Middleware 的声明顺序和 awrap 调用顺序以锁定版本的实际执行链为准，必须验证 Skills 披露 → 权限过滤 → 工具选择 → 每候选预算／计费，以及执行异常 → 重试／错误转换 → 正式结算的关系；不能仅把三个实例追加到 middleware 列表就认定完成。

待办：

- [ ] 保留主 Agent 回答和工具调用形式、唯一主图、原权限和正式事件顺序。
- [ ] 工具选择只使用允许且已披露的候选，必需工具保留、非法名处理和选择失败退路可验证；选择结果不会被 registry 全量追加覆盖。
- [ ] 选择模型逐次计费，同一逻辑主请求重试／切换不重复筛选；最终 Schema、预算、摘要哈希和界面容量与真实请求一致。
- [ ] 按配置接入官方 fallback；主模型重试、备用次序、无配置／全部失败／不兼容候选及非 Provider 错误停止均可验证。
- [ ] 备用模型真实身份、请求、用量、价格、流式 partial、消息适配及窗口重新计量可追踪，不重跑已完成工具或修改持久首选模型。
- [ ] 工具错误组件与现有只读重试、稳定 error_code、重复失败阻断和结算共用一条路径，唯一工具结果保留 call ID、输出和副作用状态。
- [ ] 审批中断、取消、关键 Hook／快照／输出／JSONL 失败不被转成普通错误继续运行，所有工具来源有行为验证。
- [ ] 不因模板、选择、切换或错误转换绕过 ModelRequestRunner／ToolSettlementMiddleware，也不叠加重复 SDK 重试或计费。

## 八 JSON 长期记忆、官方 Store Manager 与主动工具

本节是用户确认的记忆功能调整方案。记忆只保留 JSON 内容文件，替代三份 Markdown 以及原有逐条 MD＋JSON 存储；接入官方 create_memory_store_manager、create_manage_memory_tool、create_search_memory_tool。保留来源校验、用户／项目作用域、受控模型调用、计费、后台生命周期和上下文投影。对外流程保持“读取未处理来源 → 整理记忆／按需更新规则 → 校验并保存”三步；后台沿用 asyncio 调度，规则优化使用 Prompt 和单／多提示词优化器。不属于仅保持调用次数和输出完全相同的 LCEL 等价重构。

### 文件与唯一内容来源

每个独立作用域保存一个 memory.json，三类记忆通过记录类型区分。用户与每个项目的目录继续按现有配置隔离，不为用户／项目混用同一个内容文件。

```text
<用户记忆目录>/memory.json
<当前项目记忆目录>/memory.json
```

不维护 semantic.md、episodic.md、procedural.md、逐条内容 MD 或 MEMORY.md 索引，不为每条记忆单独创建内容 JSON。JSON 是唯一活动内容来源，界面和记忆工具均读取同一 Store。必要的版本备份、删除恢复记录、作业状态和事务数据仍可使用 JSON；这些内部数据不参与正常召回，不形成第二份活动内容真源。原始会话 JSONL、工具结果与已有审计记录继续保留。旧数据在迁移验证完成前不删除，迁移后只作为恢复依据。

### 记录结构与三类记忆

文件包含 schema_version、revision、records 和已成功提交的批次／来源进度。每个 records 条目以稳定 ID 为键，包含 value、created_at、updated_at。value 采用可转换为 LangMem 对象的 kind＋content 结构；示例格式需在固定版本接口验证后落实。

```json
{
  "schema_version": 1,
  "revision": 12,
  "records": {
    "9a17c7c906ef49c596552478352fd15d": {
      "value": {
        "kind": "SemanticMemory",
        "content": {
          "title": "代码讲解偏好",
          "summary": "喜欢最小示例，希望看清参数传递。",
          "body": "使用直接执行的最小示例，解释参数来源、传递位置和返回值。",
          "sources": [
            {"session_id": "session-a", "entry_id": "entry-18", "quote": "解释参数怎么传"}
          ]
        }
      },
      "created_at": "2026-10-13T22:00:00+08:00",
      "updated_at": "2026-10-13T22:00:00+08:00"
    }
  },
  "processed_batches": {}
}
```

SemanticMemory 保存事实、偏好、项目知识；EpisodicMemory 保存情况、可观察的实际动作、结果、适用条件、来源和验证状态；ProceduralMemory 保存适用任务与行为规则。使用 Pydantic schema 校验字段、长度和数量。来源存在不等于支持结论，还需检查引文和内容支持关系。不提取模型隐藏推理，不把正常结束视为已验证成功。

调用与查找统一使用 namespace＋key。已有 ID 迁移后保持稳定；新增 ID 接受框架生成的合法标识并保持不变，不能保存时再次分配另一个 ID。key 在同一 namespace 下跨类型唯一，类型变更需明确校验。存储保留原始创建时间和更新版本，不依赖文件修改时间。

### JsonMemoryStore 与 BaseStore 适配

新增 JsonMemoryStore，继承 langgraph.store.base.BaseStore，按所选版本实现 batch／abatch。框架 get／search／put／delete／list_namespaces 及异步方法通过这些入口分派；返回值顺序对应输入操作。

| 操作 | JSON 存储实现 |
| --- | --- |
| GetOp | 按 namespace＋key 读取记录，返回 Item；不存在返回 None |
| SearchOp | 限定 namespace 前缀和字段过滤，查询相关条目，分页后返回 SearchItem |
| PutOp，value 非空 | 校验并新增／更新记录，保留稳定 key 和创建时间 |
| PutOp，value 为 None | 校验目标与证据，删除记录并保存可恢复版本 |
| ListNamespacesOp | 按允许访问的作用域、前缀／后缀条件和分页列出 namespace |

namespace 由运行时可信的用户／项目身份绑定，例如 ("memories", "user", user_id)、("memories", "project", project_id)。目录映射来自配置，不将任意 namespace 拼成磁盘路径。查询前缀、分页和过滤不能突破当前允许作用域；非法操作明确报错，不能静默忽略过滤或越权目标。

官方管理器、主动记忆／搜索工具、初始召回和规则优化共用 Store 及同一校验／提交服务。适配层统一处理管理器 kind＋content 和主动工具 schema 输出之间的转换，读回对象必须能被管理器识别并更新。不得因两种写入来源的包装差异产生重复记录或不可更新的条目。

Store 只组织存储、检索和受控校验，不能在 put／delete 中递归启动记忆提取。TTL、index 等可选能力按公开接口明确声明支持范围；不声称提供未实现的自动过期或向量索引。同步／异步入口及关闭／取消收拢按项目运行方式验证，不能在已有事件循环里直接 asyncio.run。

### 统一查询：目录模型筛选

```text
Store 收到 query、namespace、filter、limit、offset
→ 读取一致的 JSON 快照，过滤允许作用域和记录字段
→ 程序提取 key、kind、标题、摘要，形成目录
→ 受控模型选择相关 ID／相关性顺序
→ 程序校验 ID、去重、应用分页及返回预算
→ 读取正文并返回 SearchItem
```

继续不使用 Embedding、向量数据库或人工同义词表，不沿用关键词排序为主检索路径。无 query 时按明确且稳定的顺序列出符合过滤条件的记录，无需模型调用。查询可返回空结果；空目录跳过模型请求。目录超预算时分批筛选并有界汇总，不能静默截掉后半目录；每次查询限定最大条目数、总正文长度和模型调用预算。

Prompt Optimizer 不负责检索。筛选失败时，初始召回记录失败并以无新增记忆继续主任务；主动搜索返回正式工具错误；后台管理器检索失败则失败该批次，不按“没有旧记忆”继续新增并推进进度。预算不足也不能冒充空结果。

create_memory_store_manager 通过 Store 查询旧记忆，外层不再另跑“新材料＋目录定位旧条目”的重复模型步骤。query_model 如启用，其用途仅是生成检索查询，不能冒充存储的相关性选择；初版不额外启用，实际内部查询与模型调用逐次结算。

### 任务开始：初始召回一次

用户新消息先写入原始历史，再通过同一 Store 查询用户及当前项目记忆，记录 memory_load 快照，由 ContextProjector 注入初始记忆。每轮开始自动召回一次，后续工具循环携带该快照；下一轮替换初始记忆块，不累积所有旧快照，不全文加载整个文件。

初始召回由唯一入口承担，MemoryMiddleware 不重复加载。情景案例标注为历史参考，项目事实保留来源和时间，行为规则受当前明确要求、项目作用域和既有权限边界约束。

### 执行中：官方主动记忆和搜索工具

在现有 create_deep_agent 工具入口注册 create_manage_memory_tool 和 create_search_memory_tool，按用户／项目作用域配置官方实例和工具名，绑定同一个 Store；不另建主 Agent 图或业务循环。工具 namespace 和访问权限由运行时确定，不能由模型任意跨项目指定。

- 搜索：任务出现新问题、初始召回不足或需要核实旧记忆时按需补查，不每次模型调用自动搜索。结果作为正式工具结果进入原始历史与 ContextProjector；不再把相同正文追加为另一份 memory_load。
- 管理：明确要求记住、纠正或忘记某项信息时，或出现有依据的长期事实／已验证案例时，允许执行中新增、更新、删除。工具返回成功前必须完成可靠提交；无效来源、临时要求或越权修改返回可解释的失败。
- 统一校验：工具 schema 包含类型、适用条件及来源等必要字段。服务从当前任务的可信历史补充会话与来源上下文，模型提供的任意来源 ID 不直接作为真实证据。删除也校验目标、来源和版本，不能仅凭一个 key 删除。
- 去重：初始记忆与搜索结果按 namespace＋key＋版本去重并限制正文预算，同条目的新版本可以替换旧版本。去重针对模型可见正文，不删除正式工具调用／结果记录，也不破坏配对和回读。
- 结算：沿用已有工具权限边界、记录、错误处理和计费；正常主会话记忆变更无需人工批准。评测与隔离 Worker 的原有记忆禁用策略继续生效，不能通过主动工具绕过。

### 任务结束：读取、整理、保存三步

主 Agent 的最终回答和工具正式结果继续保存到 JSONL，并按现有流程在聊天界面展示。后台只整理长期记忆，不额外生成与最终回答重复的任务报告；不接入 create_thread_extractor，不新增任务详情页面或额外会话标题／摘要生成调用。80% 提前摘要继续由原有 SummaryService 管理。

```text
主任务完整结算，正常展示最终回答
→ asyncio.create_task 启动独立记忆后台任务
→ 读取：按持久进度选择未处理的对话、反馈和必要工具结果
→ 整理：Store Manager 处理语义／情景；有长期行为反馈时更新程序规则
→ 保存：校验、去重、版本检查，提交 JSON 与成功来源进度
```

后台启动沿用 AgentSession → MemoryService.settled(run_id) → asyncio.create_task 的现有边界。每个任务保留引用与来源批次身份，任务字典仅负责进程内生命周期，不代替持久进度。本次不引入 ReflectionExecutor、额外后台线程或远端整理服务；关闭时取消并等待任务收拢，失败／取消记录 pending_retry。同作用域的后台更新按既有锁和串行协调方式执行，主动工具仍使用统一版本检查；不在等待模型时持有磁盘文件锁。

### 第一步：读取未处理来源与最新状态

后台真正开始处理时，按会话／分支和作用域读取持久进度，确定本批尚未处理的来源 ID，捕获不可变来源快照并读取最新 JSON 版本。批次有来源与 Token 上限；未纳入本批的消息仍保持未处理，不能只取最后一条输入或把被预算截掉的材料标记完成。每个作业构造独立模型生命周期和 Store 更新视图，不共享可变请求记录、用量状态或暂存变更。

失败批次在初始化或下一次记忆处理时按持久身份核对后重新安排。恢复只重试内部记忆整理，不执行旧业务工具或恢复已过期的用户审批；已成功提交的来源不得重复新增记忆。

### 第二步：Store Manager 整理事实和案例

```text
本批新对话和来源信息
→ create_memory_store_manager 发起旧记忆查询
→ JsonMemoryStore.asearch：目录模型筛选、校验 ID、读取正文
→ 管理器内部模型比较新材料与旧记忆
→ 新增／合并／纠正／删除暂存到本作业 Store 视图
```

Store Manager 是唯一后台语义／情景整理入口，项目不再并行调用旧提取器或单独的 create_memory_manager。它调用统一 Store 检索，外层不再额外先定位一次旧条目。所选版本可能按不同对话窗口发起多个查询，查询结果需有相关性顺序／稳定评分供组件汇总；所有查询、整理和修复请求逐次记录实际用量，不能假设一次 manager 调用只发生一次模型请求。

语义与情景使用经接口验证的 schema；本步骤不自行改写程序行为规则。主动写入不表示整轮来源已经处理完成，后台读取最新记录、补充来源和遗漏，不能重复新增已经保存的主题。无新信息允许无内容变更地记录本批已处理；存储／校验失败则保留对应来源待处理。

### 有长期行为反馈时：Prompt 与单／多规则优化

通过统一 Store 查询相关 ProceduralMemory 后，用 Prompt 包装已读取的规则。Prompt.name 与 namespace＋原记忆 ID 建立唯一映射，prompt 为正文，when_to_update 描述适用反馈条件，update_instructions 限定允许修改的范围。Prompt 是数据对象，自身不调用模型；它的名称不代替作用域检查，未读取的条目不得被优化器猜测或覆盖。

```text
本批对话／长期反馈＋相关旧程序规则
→ 无长期反馈或仅临时要求：跳过优化
→ 一条相关规则：create_prompt_optimizer(kind="prompt_memory")
→ 多条相关规则：create_multi_prompt_optimizer(kind="prompt_memory")
→ 单条按输入 Prompt 的身份映射，多条按返回 Prompt.name 映射，校验并暂存正文
```

单／多优化器是互斥选择，同批规则不先逐条优化再重复跑多优化器。初版显式选择 prompt_memory 策略；单优化器正常路径一次模型调用，重试另计；多优化器还可能包含规则归因和逐条更新，不能宣称同样只调用一次，也不先另建一轮重复的模型反馈分配流程。具体输入／返回类型按固定版本验证，将单条文本和多条命名结果分别适配回原记录，拒绝陌生 ID、错作用域和重复映射。

有明确长期反馈但没有相关旧规则时，由程序为该反馈分配新规则草案的稳定 key 和作用域，将反馈及适用条件作为输入，走单条优化分支；不凭空假设已存在旧规则。提交失败后重试复用同一批次的草案身份，避免重复创建。

优化更新的是 memory.json 中的程序规则，不训练模型或直接改写基础 system prompt 文件。程序维护原 ID、摘要、适用条件、来源和时间，经同一 Store 提交；后续任务召回相关规则并由 ContextProjector 提供给主模型，才影响执行和回答。例如“以后解释简短些、说明参数怎么传”可更新讲解规则；“仅这次回答一句话”不固化。没有行为反馈不调用优化器，不改写基础权限、工具约束或任意项目说明。

明确且范围清楚的用户要求校验后自动应用；模型自行归纳的规则先经代表性任务比较再采用。优化器返回文本不代表效果已改善。关联的语义偏好与程序规则按证据组协调，独立失败不丢弃其他有效变更，不把整个来源范围提前标记完成。

### 第三步：统一提交记忆与来源进度

Store Manager 与优化器只在独立更新会话中产生暂存修改。MemoryService 检查 schema、来源支持、作用域、重复和关联变更，再通过 JsonMemoryStore 重读版本、处理冲突并可靠提交；主动工具也使用同一提交入口。每作用域 memory.json 同步保存成功变更和对应来源进度，不把组件返回成功直接当成已经落盘。内部并发、部分失败及恢复规则见下节。

### 合并、并发提交与恢复

- 完全重复跳过或补充来源；同主题的补充合并到已有 key。有依据的纠正和删除自动处理，不确定冲突保留原记录，不转成记忆人工审批。
- 一条无效修改不丢弃同批独立有效修改；依赖同一证据、需同时生效的变更作为一组处理。部分失败逐组记录并可重试，不能把整段来源提前标记处理完成。
- 后台更新使用作业独占的 Store 更新会话／写入暂存区，记录读取快照和版本，支持读到本作业自己的暂存变更。框架可能并发调用多个 aput／adelete，暂存区需同步保护；不将一次 manager.ainvoke 或一次 abatch 自动视为事务。
- 受控整理和来源校验完成后才统一提交。获取跨进程 FileLease、重读最新文件并比较读时 revision／条目哈希；文件版本变化触发重读，相关条目冲突需要重新合并／整理，不能直接用旧快照覆盖。
- 同一作用域的三类记忆与成功批次／处理进度写入一个新 JSON 快照，复用 atomic_write 的临时文件、flush／fsync 与原子替换；文件锁和原子替换不代替读时版本检查。单个主动工具调用采用相同机制提交。

## 九 Agent 图内的 LCEL 编排

### 外层图和内部 Chain 的边界

保留 create_deep_agent 生成的主 Agent 图。模型／工具循环、图状态、interrupt／resume 和已有工具调度继续由现有框架入口承担，不再新增一个 while 主循环或第二套 Agent 图。

概念流程是：

```text

→ 固定的模型请求前处理
→ 受控模型调用
→ 根据既有工具路由执行工具
→ 下一轮或结束

后台摘要任务 → 固定摘要生成 Chain
主 Agent 执行中 → 官方记忆／搜索工具 → 同一 JSON Store
```

上述流程是职责示意，不据此调整源代码原有 Hook、输入排队和结算时机。

### 受控模型调用步骤

使用 RunnableLambda 接入现有 ModelRequestRunner，不直接用裸模型替换已计费、已记录的入口。保留 logical_id、purpose、请求编号、重试次数、Provider 原始用量、停止原因和错误转换。

### 摘要生成顺序 Chain

```text

→ 原有序列化
→ ChatPromptTemplate
→ 受控模型调用
→ 原有完整性、停止原因和工具调用检查

→ 原有摘要清理规则
→ 原有 SummaryCompletion 结果
```

保留消息 ID、工具调用与结果引用、附件引用及不完整任务前缀的序列化内容。StrOutputParser 只取出文字，不替代完整性检查、空摘要拒绝或现有摘要标签处理。

```text
生成阶段：
需要新摘要 → 启动后台生成
不需要    → 保留当前任务状态

采用阶段：
容量充足             → 继续
容量紧张且摘要有效   → 采用
```

同一次检查可能先启动后台任务，再因容量不足进入等待；不得把这两个阶段压成一个只匹配第一条的互斥分支。保留 manual、force、allow_apply、wait_for_capacity 等既有调用语义，GraphInterrupt 和取消异常不能被当成普通解析错误吞掉。

“固定内部流程”指依赖与执行规则确定，不表示所有步骤都串行。原有允许并发的独立步骤保持并发，有依赖的步骤保持顺序。框架并行器不取代现有权限、锁、工具结算或团队依赖管理。按这个边界，图内 Chain 与现有并发要求不冲突。

### 结构化输出与请求协议

仅声明模型支持结构化输出，不足以证明请求协议、字段类型转换、格式接受范围、错误路径和调用次数等价。本文件已将结构化组件替换与 LCEL 编排分开验证，保留无法等价迁移的原校验细节，避免把换解析器误认为纯写法调整。

### 长期记忆自动保存

正常主用户会话的长期记忆既支持执行中官方主动工具修改，也支持任务结束后官方 Store Manager 自动整理；两条路径共用 JSON Store、校验和提交服务。有效新增、重复合并、有依据的纠正更新和删除均自动处理，不保留记忆写入的人工审批门槛。

来源检查、作用域、版本备份、事务和并发冲突处理继续自动执行；记忆存在需要处理的变更时，系统自行重读和处理，不要求用户批准。用户查看和编辑记忆是管理能力，不是保存前置条件。其他工具／Plan 的权限审批继续保留。

### 框架和上下文不变项

依据当前代码和用户要求，保留 Deep Agents 主入口、公共 Middleware、主聊天内存 checkpoint、JSONL 长期历史、80% 两阶段摘要及唯一服务职责。LCEL 仅在这些既有入口内部表达数据流，不另建状态库、压缩器或执行循环。

### 依赖版本边界

先核对当前项目依赖中可用的公共 Runnable、模板和解析接口。版本选择依据本计划的功能需求、官方组件能力和兼容验证结果。确需升级时，单独更新依赖与锁文件并完成兼容验收，不把升级混同于 LCEL 等价重构。

### 命令补全的范围和交互

第十节只改变命令元信息管理、前缀筛选和输入候选弹窗，现有命令的业务处理与其他计划部分保持原范围。code-python 是实现参考，实际候选与入口以 pycode 的注册信息为准。

弹窗打开时 Enter 的补全事件和弹窗关闭后的提交事件必须分开；前一次 Enter 不执行命令，不把未填完的参数提交给业务入口。该行为是用户明确要求的输入交互，单独验收，不宣称与原有 Enter 直接提交完全相同。

### 新 Middleware 与既有能力

工具筛选仅减少本次主模型可见 Schema，不增加工具权限或接管 Skills／MCP 生命周期；fallback 改变实际调用模型，必须同步能力、预算和逐次计费；工具错误转换只处理执行边界内允许恢复的异常，不代替可靠结算。既有 ModelRetryMiddleware、ToolRetryMiddleware、SummaryService 和 ToolSettlementMiddleware 继续是各自职责的唯一实现，不引入第二套重试、摘要或工具结果保存路径。组件版本／参数和组合顺序需要按当前锁定栈验证，不能把官方最新文档示例当作现有版本已经支持的证据。

- 每执行一个测试命令或一轮编码评测，立即追加一条记录；通过、失败、错误、跳过、中断和未验证都要记录。
- 旧记录不可删除、覆盖或改写。修复后重跑时创建新的 `test_run_id`，并用 `supersedes` 指向旧记录。
- 每条至少保存：`test_run_id`、北京时间、测试 ID、目的、源码／提交／manifest／依赖锁哈希、操作系统、Python 与关键依赖版本、完整命令、配置摘要、模型与 thinking、开始／结束时间、耗时、通过／失败／错误／跳过数量、退出码、失败摘要、未验证原因、产物路径与 SHA-256。
- 不记录 API Key、`.env`、认证头、私人源码正文、完整提示词或无限大工具输出；敏感值只记录“已配置／未配置”。
- 同一次 full 评测的总记录引用 12 条逐题结果；逐题结果保留自己的 task ID、请求数、token、独立测试结果和 patch 哈希。
- 本地 `results.jsonl` 与 `summary.json` 是机器可读权威结果；`测试数据.md` 是索引和验收说明。两者不一致时标记失败并调查，不能手工改 Markdown 掩盖机器结果。
- 历史证据可以导入，但必须标记“历史导入，非本次重跑”，保留原报告路径和源码哈希。
- 完成本计划前，逐项核对本节测试 ID 在 `测试数据.md` 中有最新记录；缺记录视为未测试。

### LangSmith：追踪模型和工具执行

- 关联主任务、工具选择模型、主／备用模型的每次请求、工具重试／错误转换、官方主动记忆／搜索工具，以及后台摘要、Store 查询中的目录筛选、Store Manager 整理和提示优化；后台任务通过来源任务 ID 关联，不因主请求结束而丢失关联。
- 记录输入输出、耗时、错误、模型与提示版本、Token 用量，以及有可靠价格配置时的估算费用；未知费用不记为零。
- 优先复用框架已有追踪与回调，核对不会重复记录同一次调用。项目原有请求结算和计费仍是业务依据，LangSmith 用于分析和对照。
- 测试使用独立项目和合成／脱敏数据，凭据从环境配置获取；默认不上传真实用户会话、私有源码或记忆全文。
- 没有凭据或网络不可用时，本地测试和主业务仍可运行；报告明确标记云端追踪验证未执行，不计为通过。

### OpenEvals：评估输出和提示优化效果

在实际选定版本支持的评估器基础上配置评估标准，不假设安装后即可自动判定所有业务质量。

- 代码讲解：是否正确、是否说明参数来源和返回值、是否遵守最小示例等用户要求。
- 记忆整理：是否有来源支持、是否遗漏应保存的信息、是否把临时要求误记为长期规则；结合参考条目和确定性断言。
- 历史摘要：是否保留关键约束、未完成任务和必要事实，是否添加原文不存在的结论。
- 程序记忆优化：覆盖单条／多条规则选择、Prompt 身份往返、临时反馈跳过和新规则实际召回；同一组保留测试任务分别运行旧规则和新规则，比较输出质量与既有要求的遵守情况。用于生成新规则的反馈样例与最终验收样例分开，避免只记住样例。
- 能直接检查的字段、ID、证据引用和格式用普通测试检查；语义质量使用明确评分标准的模型裁判。代码正确性以实际测试结果为依据，不以裁判的好评代替运行。

### AgentEvals：评估执行轨迹

把项目记录转换成评估器支持的消息／工具调用轨迹，保留工具名、必要参数、调用与结果配对。内部框架调用按职责标注，不能把后台记忆整理误算成用户业务工具。

- 文件任务：关键读取、修改和验证步骤是否符合该测试任务的要求，有无遗漏必要动作。
- 错误路径：工具失败后是否按既定规则重试／转换和结算，有无无效重试或重复执行有副作用的动作；取消、中断和持久化失败不得作为可恢复工具错误。
- 工具选择与模型切换：核对候选权限、always_include、选择失败退路、最终 Schema 与预算；同一逻辑请求切换保持消息／工具快照，分别记录实际模型请求与费用，不重新执行已结算工具。
- 权限与恢复：未获授权的工具执行次数为零，中断／恢复后不重复执行已完成动作。
- 记忆路径：每轮初始召回一次，执行中官方搜索工具按需补查，正文按作用域／ID／版本去重且正式工具记录完整；主动记忆工具可靠提交后才报告成功。任务结束后 Store Manager 整理增量来源，不重复新增已主动保存的内容；无长期反馈时跳过优化，有反馈时按规则数互斥选择单／多优化器，不重复调用；记忆后台沿用 asyncio，不额外生成会话报告。核对统一 Store 查询、提交与来源进度，组件内部模型调用不等同于重复执行整个流程。
- 确定顺序的流程使用精确轨迹断言；允许多种解决路径的任务使用必要步骤、偏序关系或语义评估，不强制每次产生完全相同的工具序列。自定义确定性断言补充 AgentEvals 的通用评估器。
