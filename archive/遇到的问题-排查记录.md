# 项目中遇到的问题

## DeepSeek thinking 与强制 `tool_choice` 不兼容

### 问题背景

长期记忆链路需要模型返回固定结构的审核结果。例如，保存记忆前需要得到以下字段：

```json
{
  "supported": true,
  "durable": true,
  "scope_valid": true,
  "deletion_requested": false,
  "outcome_verified": false,
  "reason": "用户明确表达了长期偏好"
}
```

项目使用结构化输出适配器，把这份 Schema 转换为一个虚拟函数工具 `MemoryEvidenceVerdict`。这个工具只用于约束返回格式，不会访问文件、网络或执行命令。

适配器原本会发送类似下面的请求参数，要求模型必须调用这个固定工具：

```json
{
  "model": "deepseek-flash",
  "thinking": {"type": "enabled"},
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "MemoryEvidenceVerdict",
        "parameters": {"type": "object"}
      }
    }
  ],
  "tool_choice": {
    "type": "function",
    "function": {"name": "MemoryEvidenceVerdict"}
  }
}
```

### 现象

主聊天请求能够正常完成，但后台记忆审核请求返回 HTTP 400，导致记忆没有保存。

最小化真实请求得到的服务端错误为：

```text
Thinking mode does not support this tool_choice
```

这说明问题不在 API Key、模型名称、Schema 字段或记忆存储，而在参数组合：DeepSeek 开启 thinking 后，不接受通过 `tool_choice` 锁定某个具体工具。

### 排查过程

1. 确认相同 Key 和模型的普通聊天请求成功。
2. 检查请求账本，发现失败只发生在后台结构化请求，错误码是 `provider_http_400`。
3. 构造最小请求，只保留 thinking、一个结构化工具和固定 `tool_choice`。
4. 从 SDK 的公开异常中读取并脱敏服务端错误，确认是 thinking 与固定工具选择不兼容。
5. 排除输入过长、字段校验失败、模型不存在和网络错误。

### 根因

`model` 与 `tool_choice` 的职责不同：

- `model` 指定使用哪个模型，例如 `deepseek-flash`。
- `thinking` 控制是否启用推理模式。
- `tools` 声明本轮可使用的工具或结构化返回格式。
- `tool_choice` 控制模型如何选择工具。

thinking 模式仍然支持指定模型，也支持携带工具。冲突仅发生在下面这种“必须调用指定工具”的选择方式：

```json
{
  "tool_choice": {
    "type": "function",
    "function": {"name": "MemoryEvidenceVerdict"}
  }
}
```

### 修复方案

对于 DeepSeek 且 thinking 已启用的内部结构化请求，把固定工具选择改为：

```json
{
  "tool_choice": "auto"
}
```

同时保留以下约束：

1. 继续向模型提供完整 Schema。
2. 在系统提示中明确要求通过对应结构化工具返回。
3. 继续使用 SDK 原生结构化解析器。
4. 程序验证工具名称、必填字段、字段类型和停止状态。
5. 再校验审核结论是否由真实会话证据支持。
6. 返回普通文本、缺字段、类型错误或证据不足时，本次作业失败，不写入记忆，并保留为待重试。

这样只是把“服务端参数层强制”调整为“模型按提示选择，程序严格验收”，没有放宽最终写入条件。

### 为什么不直接关闭 thinking

关闭 thinking 虽然可以绕开参数冲突，但会擅自改变用户配置和模型行为。项目选择保留 thinking，并根据 Provider 的公开能力调整工具选择参数。这样主聊天与后台任务使用一致的模型配置，也避免为了结构化输出再设计另一套模型调用路径。

### 为什么不能只相信模型返回的 JSON

结构正确不代表内容可信。项目还需要执行独立的程序校验：

- 引用的会话 ID 和消息 ID 必须真实存在。
- 引文必须出现在原始用户消息或已配对的工具结果中。
- 临时要求、秘密和助手自行声称的成功不能进入长期记忆。
- 用户偏好、项目事实和行为规则必须写入正确作用域。
- 最终写入必须经过版本检查、写入许可和原子提交。

因此，Schema 只解决“返回格式是否正确”，证据策略解决“内容是否有资格保存”。

### 验证

修复需要覆盖以下场景：

- DeepSeek thinking 开启时，请求使用 `tool_choice="auto"`。
- thinking 配置仍随请求发送，没有被关闭。
- 模型按 Schema 返回时，原生解析和用量记录正常。
- 模型未调用结构化工具或返回不完整字段时，审核失败且不写入记忆。
- OpenAI、Anthropic 和 DeepSeek 非 thinking 场景保持原有协议行为。
- 真实 DeepSeek 完整会话能够完成前台回复、后台审核、记忆保存和下一会话召回。

### 面试回答示例

> 我在接入 DeepSeek 的长期记忆审核时遇到过一个 Provider 能力兼容问题。主聊天正常，但 thinking 模式下的结构化审核请求一直返回 HTTP 400。通过请求账本和最小化真实请求，我确认不是 Key、Schema 或上下文长度问题，而是 thinking 模式不支持用 `tool_choice` 锁定某个具体函数。我的处理不是关闭 thinking，也没有增加一套备用调用链，而是把该 Provider 的固定工具选择改为 `auto`，同时保留 Schema、原生解析、停止状态检查和证据校验。这样既遵守了 DeepSeek 的接口限制，也没有降低记忆写入安全性。随后我用协议回归和真实模型会话分别验证了参数、用量、失败不落盘以及后续召回。

### 可以继续追问的设计点

如果面试官继续追问，可以说明：

- `tool_choice="auto"` 可能让模型不调用工具，因此程序必须把“没有结构化结果”视为失败，不能尝试猜测或从自由文本中提取。
- Provider 能力差异应该封装在模型适配边界，不能散落到记忆业务代码中。
- 请求失败也必须结算并记录真实 Provider、模型、请求用途、重试和 token 用量。
- 后台失败不能推进来源游标，否则会永久漏掉尚未保存的长期信息。
